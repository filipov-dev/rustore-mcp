# Решение проблем

Ошибки HTTP-режима (`401` без токена доступа, `403` по `Host` и `Origin` и другие) описаны в [HTTP-режиме](http.md#проверка).

## Homebrew не ставит формулу из стороннего tap

Устанавливайте по полному имени, а tap добавляйте с полным адресом: он размещён на SourceCraft, а не на GitHub.

```bash
brew tap filipov-dev/tap https://git.sourcecraft.dev/filipov-dev/homebrew-tap.git
brew install filipov-dev/tap/rustore-mcp
```

## macOS: Keychain спрашивает разрешение

macOS может спросить, разрешить ли `rustore-mcp` доступ к записи `dev.filipov.rustore-mcp` в связке ключей, — обычно когда ключ сохранила одна сборка бинарника, а читает другая. Нажмите «Всегда разрешать», иначе вопрос будет повторяться при каждом запуске сервера.

Бинарник из Homebrew и релизных архивов подписан Developer ID, поэтому после обновления разрешение, как правило, сохраняется. Бинарник, собранный из исходников, не подписан: после каждой пересборки macOS считает его новой программой и спрашивает снова.

Когда сервер запускает MCP-клиент, окно с вопросом появляется поверх других окон, а клиент ждёт ответа. Если клиент пишет, что сервер не запустился или не ответил, проверьте, нет ли такого окна.

## Linux: Secret Service недоступен

В Linux ключ хранится через Secret Service (D-Bus); `libdbus-1` не нужна. Ошибка `no Secret Service (org.freedesktop.secrets) is available …` при `connect`, `auth` или `serve` означает одно из:

- в сессии не запущен провайдер Secret Service — GNOME Keyring, KeePassXC (с включённой интеграцией Secret Service), KWallet и т. п.;
- нет сессионной шины D-Bus: например, при входе по SSH на сервер без графической сессии;
- связка ключей заблокирована и разблокировать её некому.

Запасного файлового хранилища нет, и хранить ключ в переменной окружения или файле нельзя — это намеренное ограничение. Варианты:

- запустить провайдер вручную ([Linux без Secret Service](cli.md#linux-без-secret-service): `dbus-run-session` и `gnome-keyring-daemon --unlock`);
- запустить `rustore-mcp` на рабочей машине с графической сессией;
- использовать [HTTP-режим](http.md) в контейнере: там ключ читается из файла секрета `--key-file` с правами `0600`.

## Linux: ошибка проверки сертификата

Сертификат RuStore API проверяется по корневым сертификатам системы. Если запросы к API падают с ошибкой TLS или сертификата, проверьте, что они установлены: в минимальных образах (Debian/Ubuntu slim и т. п.) их нет: поставьте пакет `ca-certificates` или укажите файл сертификатов в переменной `SSL_CERT_FILE`.

## Работа по SSH

- По SSH `connect` и `auth login` спрашивают путь к файлу ключа в терминале; файл можно передать и флагом `--key-file` или через stdin (`auth login --key-stdin`).
- В Linux по SSH обычно нет сессии D-Bus и Secret Service — см. [выше](#linux-secret-service-недоступен).
- В macOS по SSH связка ключей входа может быть заблокирована: разблокируйте её (`security unlock-keychain`) или выполните `connect` в обычном сеансе.
- В Windows Credential Manager есть только в сеансе, вошедшем с паролем: в SSH-сеансе со входом по ключу, в службе или задаче планировщика без сохранённого пароля `auth` и `serve` падают с ошибкой «A specified logon session does not exist». Выполните `connect` и запускайте MCP-клиент в обычном сеансе пользователя ([Windows](clients.md#windows)) или используйте [HTTP-режим](http.md).

## «no RuStore API key is stored for profile …»

Для профиля из `serve --profile` нет ключа в системном хранилище. Проверьте имя профиля в конфигурации клиента и сохраните ключ:

```bash
rustore-mcp auth status --profile <профиль>
rustore-mcp auth login --profile <профиль> --key-file <файл ключа>
```

Профиль по умолчанию для `serve`, `auth` и `connect` — `default`. `rustore-mcp serve --status --profile <профиль>` покажет, есть ли у профиля ключ.

## «… holds only the private key» или «is not a usable RuStore API key»

- В файле только приватный ключ без keyId: передайте его флагом `--key-id <ID>` (keyId показан рядом с ключом в консоли RuStore) или сохраните файл как JSON `{"keyId": "…", "privateKey": "…"}`.
- Файл не похож на ключ RSA: в нём должен быть текст Base64 из консоли RuStore (DER PKCS#8 или PKCS#1) или PEM. Ключ короче 2048 бит не принимается. Фрагменты ключа в сообщение об ошибке не попадают.

## RuStore отклонил ключ

`connect`, `auth login` или `auth status` пишут `RuStore rejected the API key (HTTP …)`, либо инструмент возвращает такую ошибку. RuStore не выдал токен:

- **The signature did not verify** — приватный ключ не от этого keyId. Проверьте, что keyId и приватный ключ взяты от одного ключа в консоли RuStore, или создайте новый ключ.
- **Check the key ID** — ключа с таким keyId нет: он удалён или истёк.
- **RuStore rejected the time of the token request** — часы машины расходятся с настоящим временем больше чем на минуту: включите автоматическую установку времени.

Замените сохранённый ключ:

```bash
rustore-mcp auth login --profile <профиль> --key-file <файл ключа>
```

Сервер читает ключ из хранилища при запуске, поэтому после замены перезапустите его: переподключите сервер в клиенте (`/mcp` в Claude Code) или перезапустите клиент.

## Нет доступа: HTTP 403

RuStore выдал токен, но `auth login` или `auth status` пишут `the key has no access to GET /public/v1/application`, либо инструмент возвращает ошибку `403`: у ключа не отмечен нужный метод API или приложение. Откройте ключ в консоли RuStore («Компания → RuStore API»), отметьте методы, которые нужны агенту (для проверки — хотя бы список приложений), и приложения, с которыми он работает. Права ключа применяются в RuStore, сохранять ключ заново не нужно.

## Агенту не хватает инструмента

- Инструмент записи или удаления не зарегистрирован: сервер работает только на чтение. Вызов по имени возвращает ошибку с нужным флагом. Перезапустите сервер с `--allow-write` или `--allow-destructive`, например повторным `connect … --allow-write`.
- Инструмент из выключенного набора: агент найдёт его через `api_search`, в ответе сказано, каким `--toolsets` его включить. Вызвать операцию в пределах уровня доступа можно и через `api_request`.
- Инструментов с локальными файлами (`upload_apk`, `upload_aab`, `upload_icon`, `upload_screenshot*`, `export_reviews_csv`, `upload_build`, `reviews_export`, `listing_export`, `listing_apply`, `sync_screenshots`) нет в HTTP-режиме: там локальные файлы выключены.

## Клиент не видит сервер или его инструменты

- Перезапустите клиент после `connect` или правки конфигурации.
- Укажите в конфигурации клиента абсолютный путь к бинарнику (`command -v rustore-mcp`).
- Запустите команду из конфигурации вручную, например `rustore-mcp serve --profile codex`. Ошибки запуска (нет ключа, неизвестный набор, несуществующий каталог в `--allow-path`) печатаются в stderr. Если ошибок нет, сервер ждёт сообщений MCP на stdin — остановите его `Ctrl-C`.
- Для подробных логов добавьте в аргументы сервера `--log-level debug`. Логи пишутся в stderr.

## Файл «is outside the allowed directories»

Инструменты работают с локальными файлами только в рабочем каталоге сервера, системном временном каталоге и каталогах из `--allow-path`. Если клиент запускает сервер в домашнем каталоге или в `/`, рабочий каталог не разрешён. Добавьте нужный каталог в аргументы сервера: `--allow-path /path/to/project` ([Безопасность](security.md#локальные-файлы)).

## Ответ слишком большой

Ответ API больше `--max-response-bytes` (256 КиБ по умолчанию) возвращается ошибкой с подсказкой сузить запрос. Уменьшите `size` или `pageSize`, отфильтруйте по статусу или дате, листайте [постранично](tools.md#постраничная-выдача) или оставьте нужное [фильтром `jq`](tools.md#фильтр-ответа-jq). Лимит можно увеличить флагом `--max-response-bytes` в аргументах сервера.

## Запрос «Incorrect data format» или 400

RuStore отклонил аргументы. Проверьте схему инструмента (`api_search` с `tool_name`) и страницу справочника по ссылке в описании инструмента: тело запроса передаётся в `body`, списки статусов (`versionStatuses`) — строкой через запятую, даты — в формате из справочника.
