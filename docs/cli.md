# Справочник CLI

```text
rustore-mcp <команда> [флаги]
```

| Команда | Назначение |
| --- | --- |
| [`connect`](#connect) | Подключить сервер к Claude Code или Codex одной командой. |
| [`serve`](#serve) | Запустить MCP-сервер через stdio или по HTTP ([`--http`](#serve---http)). |
| [`auth`](#auth) | Управлять ключами RuStore API профилей: `login`, `status`, `logout`; `check` — какие разделы API и приложения доступны ключу. |
| [`key exec`](#key-exec) | Запустить другую программу (Gradle-плагин публикации RuStore, fastlane, скрипт) с ключом профиля во временном файле. |
| [`tools`](#tools) | Показать и проверить пользовательские инструменты из `tools.toml`: `list`, `check`. |
| [`call`](#call) | Вызвать инструмент сервера из консоли с правами профиля; без инструмента — список инструментов. |
| [`ui`](#ui) | Интерактивный просмотр профилей: настройки, права и их одобрение, регистрации в клиентах, права ключа, инструменты. |

`rustore-mcp --version` печатает версию, `rustore-mcp <команда> --help` — справку по команде.

## Профили

Профиль — имя, под которым хранятся ключ RuStore API одной компании и настройки сервера. Профиль по умолчанию — `default`, другой выбирается флагом `--profile`. Для каждого ключа компании используйте свой профиль.

- **Ключ** — keyId и приватный ключ RSA — только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Сервис `dev.filipov.rustore-mcp`, учётная запись — имя профиля; в Windows ключ хранится байтами UTF-8 и, если не помещается в одну запись, частями (`<профиль>/part-2` и далее). Ключ принимается только из файла или stdin, не из аргументов командной строки и не из переменных окружения; в `profiles.toml` он не пишется и не печатается ни одной командой. Команды показывают только замаскированный keyId (`abcd***wxyz`) и размер ключа.
- **Токен** RuStore API (JWE, живёт несколько минут) сервер получает сам: подписывает запрос `POST /public/auth/` приватным ключом (SHA512withRSA) и держит токен только в памяти процесса, обновляя его до истечения срока.
- **Настройки** (без ключа) — в `~/.config/rustore-mcp/profiles.toml`; в Linux учитывается `XDG_CONFIG_HOME`, в Windows файл лежит в `%APPDATA%\rustore-mcp\profiles.toml`. Файл создают `connect` и `auth login`:

  ```toml
  [profiles.default]
  client = "codex"                 # клиент, в котором профиль зарегистрирован через connect
  packages = ["com.example.app"]   # имена пакетов по умолчанию, их видит агент; необязательно
  allow_write = false              # права профиля: запись
  allow_destructive = false        # права профиля: удаление и публикация
  allow_path = ["/Users/me/builds"] # дополнительные каталоги для файлов; необязательно
  toolsets = []
  ```

`allow_destructive = true` подразумевает запись: при сохранении профиля `allow_write` выставляется тоже.

**Права профиля** (`allow_write`, `allow_destructive`, `allow_path`) — граница доступа stdio-сервера: `serve`, `call` и `ui` не дают больше. Меняет их `rustore-mcp ui` (или `connect --allow-write`/`--allow-destructive`, или правка файла). На macOS права сверх чтения действуют только после одобрения владельцем: одобренная копия прав хранится в Keychain (сервис `rustore-mcp.access`, учётная запись — имя профиля), а `ui` и `connect` при повышении прав спрашивают Touch ID или пароль пользователя macOS. Понижение прав одобрения не требует. Если права в профиле шире одобренных, действует пересечение; если одобрения нет или Keychain недоступен — только чтение, сервер предупреждает в stderr. В Linux и Windows одобрения нет: права ограничивают методы и приложения ключа в консоли RuStore ([Безопасность](security.md#уровни-доступа)). К HTTP-режиму права профиля не относятся: там уровень задают флаги [`serve --http`](#serve---http).

Имя профиля: 1–64 символа из `A-Z`, `a-z`, `0-9`, `.`, `_`, `-`, не начинается с `-`.

### Ключ RuStore API

Ключ создаёт владелец или администратор компании в консоли RuStore: «Компания → RuStore API». При создании отметьте методы API, которые нужны агенту, и приложения, с которыми ключ может работать, и сохраните приватный ключ в файл: консоль показывает его один раз. Файл ключа для `rustore-mcp` — один из двух форматов:

- JSON `{"keyId": "<keyId>", "privateKey": "<приватный ключ>"}` или `{"key_id": "<keyId>", "client_secret": "<приватный ключ>"}` (файл `credentialsPath` Gradle-плагина публикации RuStore, его же пишет [`key exec`](#key-exec));
- только приватный ключ — текст Base64 из консоли (DER PKCS#8 или PKCS#1) или PEM (`BEGIN PRIVATE KEY`, `BEGIN RSA PRIVATE KEY`); keyId тогда передаётся флагом `--key-id` или, в терминале, ответом на вопрос.

Ключ RSA короче 2048 бит не принимается. Файл ключа больше 16 КиБ — ошибка.

### Linux без Secret Service

Запасного файлового хранилища нет. Если в сессии нет демона Secret Service (`org.freedesktop.secrets` на сессионной шине D-Bus), команды `auth` завершаются ошибкой с подсказкой. Запустите демон хранилища: GNOME Keyring, KDE Wallet или KeePassXC с интеграцией Secret Service. На машине без графической сессии можно поднять шину и разблокированное хранилище вручную:

```bash
dbus-run-session -- sh
# внутри новой оболочки; пароль хранилища читается из stdin
gnome-keyring-daemon --unlock --components=secrets
```

## connect

```text
rustore-mcp connect <claude-code|codex> [флаги]
```

Подключает сервер к MCP-клиенту: создаёт или обновляет профиль, сохраняет ключ RuStore API и после подтверждения добавляет сервер в конфигурацию клиента. Ключ не проходит через агента и не попадает в конфигурацию клиента: туда записывается только команда

```text
<путь к rustore-mcp> serve --profile <профиль> [--toolsets <a,b>] [--dynamic-toolsets]
```

Флагов доступа в записи клиента нет: `serve` берёт права из профиля. Повторный `connect` переписывает регистрацию старых версий, в которой были флаги доступа, на команду без них.

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--profile <имя>` | `default` | Профиль: один профиль — один ключ компании. |
| `--name <имя>` | `rustore` для профиля `default`, `rustore-<профиль>` для остальных | Имя сервера в конфигурации клиента: 1–17 символов из `A-Z`, `a-z`, `0-9`, `_`, `-`. Предел 17 символов нужен, чтобы полное имя инструмента `mcp__<сервер>__<инструмент>` укладывалось в 64 символа. |
| `--scope <user\|project>` | `user` | `user` — для всех проектов пользователя; `project` — в `.mcp.json` текущего каталога (только Claude Code). |
| `--allow-write` | права не меняются | Поставить профилю уровень записи. |
| `--allow-destructive` | права не меняются | Поставить профилю уровень удаления и публикации; включает запись (в профиль сохраняются оба флага). |
| `--toolsets <a,b,…>` | набор `serve` по умолчанию | Наборы инструментов; неизвестный набор — ошибка. |
| `--dynamic-toolsets` | выкл. | [Динамические наборы](tools.md#динамические-наборы): при запуске только поиск, запросы и управление наборами, остальное агент включает сам. Нужен клиент, который перечитывает список инструментов по уведомлению. |
| `--key-file <путь>` | спросить в терминале | Файл ключа RuStore API ([форматы](#ключ-rustore-api)). |
| `--key-id <ID>` | из файла или вопрос | keyId ключа, если в файле только приватный ключ. |
| `--package <имя>` | из профиля | Имя пакета приложения по умолчанию (флаг повторяется); его видит агент. |
| `-y`, `--yes` | выкл. | Не задавать вопросов «да/нет»: оставить рабочий сохранённый ключ и записать конфигурацию клиента. |
| `--no-verify` | выкл. | Сохранить ключ без проверки запросом к RuStore API. |

Шаги:

1. **Ключ.** Если в хранилище уже есть ключ профиля и он проходит проверку, `connect` предлагает его оставить (с `--yes` — оставляет). Иначе читает файл `--key-file` или, в терминале, спрашивает путь к нему (и keyId, если в файле только приватный ключ). Ключ проверяется: сервер получает токен и запрашивает список приложений `GET /public/v1/application`. Если проверка не прошла, ничего не сохраняется, а сообщение подсказывает, что отметить у ключа в консоли RuStore.
2. **Профиль.** В `profiles.toml` записываются клиент, имена пакетов, наборы инструментов и `dynamic_toolsets` из флагов `connect` (наборы и `dynamic_toolsets` перезаписываются при каждом запуске). Права профиля меняются, только если задан `--allow-write` или `--allow-destructive`; без них профиль сохраняет прежние права (у нового профиля — только чтение). На macOS повышение прав спрашивает Touch ID или пароль; при отказе профиль сохраняет прежние права, а ключ и регистрация всё равно сохраняются.
3. **Конфигурация клиента.** `connect` показывает, что именно будет записано, и спрашивает подтверждение; при отказе (или без ответа) конфигурация не меняется, а ключ и профиль остаются.
   - **Claude Code** — через его CLI: `claude mcp add --scope <scope> <имя> -- <путь> serve --profile <профиль> …`. Файлы Claude Code напрямую не правятся. Если сервер с таким именем уже есть и запускает `rustore-mcp`, он заменяется (`claude mcp remove` и снова `add`) после подтверждения.
   - **Codex** — таблица `[mcp_servers.<имя>]` в `$CODEX_HOME/config.toml` (по умолчанию `~/.codex/config.toml`):

     ```toml
     [mcp_servers.rustore]
     command = "/opt/homebrew/bin/rustore-mcp"
     args = ["serve", "--profile", "default"]
     ```

     Остальные записи, комментарии и форматирование файла сохраняются; запись с тем же именем заменяется на месте.

   Запись с тем же именем, которая запускает другой сервер, а не `rustore-mcp`, заменяется только после явного ответа в терминале; с `--yes` `connect` завершается ошибкой и ничего не меняет. Чтобы подключить сервер рядом с ней, выберите другое имя через `--name`.
4. **Файл ключа.** В терминале `connect` в конце предлагает удалить исходный файл ключа (по умолчанию — нет: консоль RuStore показывает приватный ключ только при создании, и файл может быть единственной копией). Без терминала файл не трогается.

После подключения перезапустите клиент. В конфигурацию записывается абсолютный путь к запущенному бинарнику без раскрытия symlink: при установке через Homebrew путь `bin/rustore-mcp` переживает обновления.

## serve

```text
rustore-mcp serve [--profile <имя>] [--allow-write] [--allow-destructive]
                  [--toolsets <набор,...>|all] [--dynamic-toolsets]
                  [--tools-file <путь>]... [--allow-path <каталог>]...
                  [--timeout <секунды>] [--max-response-bytes <байты>]
                  [--log-level <уровень>] [--status]
```

Запускает MCP-сервер через stdio: MCP-клиент (Claude Code, Codex и другие) запускает команду сам и общается с ней через stdin и stdout. HTTP-режим описан ниже, в [`serve --http`](#serve---http). Каждая операция RuStore API из встроенной спецификации — отдельный инструмент; имя инструмента — `operationId` операции в snake_case (`list_versions`, `create_draft_version`, `reply_to_review`). Поверх операций есть [составные инструменты](tools.md#составные-инструменты) (`upload_build`, `release_submit`, `release_rollout`, `reviews_summary` и другие), а всегда доступны `api_search` (поиск по всем операциям) и `api_request` (запрос к любому пути API в пределах уровня доступа), см. [MCP-инструменты](tools.md#api_search-и-api_request).

Ключ RuStore API берётся только из профиля (`--profile`, по умолчанию `default`) в системном хранилище; имена пакетов по умолчанию — из `profiles.toml`. Если ключа нет, сервер не запускается и подсказывает команду `auth login`. Токен RuStore API сервер получает по ключу перед первым запросом, держит только в памяти, обновляет до истечения срока, а после ответа `401` один раз повторяет запрос с новым токеном. Ни ключа, ни токена в аргументах инструментов нет.

Если у профиля сохранены проект и сервисный токен push ([`auth push login`](#auth-push)), сервер берёт и их: они нужны только набору `push`. Без них сервер запускается как обычно, а инструменты push отвечают, как их настроить.

| Флаг | Назначение |
| --- | --- |
| `--profile <имя>` | Профиль с ключом RuStore API. |
| `--allow-write` | Сузить права профиля до записи (профиль должен её разрешать). С `--http` — регистрировать инструменты, которые создают и меняют данные. |
| `--allow-destructive` | Оставить уровень удаления (профиль должен его разрешать); включает запись. С `--http` — регистрировать и удаляющие инструменты. |
| `--toolsets <набор,...>` | Наборы инструментов через запятую или `all`. С `--dynamic-toolsets` — наборы, включённые при запуске. |
| `--dynamic-toolsets` | [Динамические наборы](tools.md#динамические-наборы): при запуске только `api_search`, `api_request`, `list_toolsets`, `enable_toolset`, `disable_toolset` и пользовательские инструменты; наборы агент включает сам. Не сочетается с `--http`. |
| `--tools-file <путь>` | Дополнительный файл [пользовательских инструментов](tools.md#пользовательские-инструменты) в формате `tools.toml`; флаг повторяется. В HTTP-режиме читаются только эти файлы. |
| `--allow-path <каталог>` | Оставить из каталогов `allow_path` профиля только этот (он должен лежать внутри каталога профиля); флаг повторяется. |
| `--timeout <секунды>` | Таймаут одного запроса к API, по умолчанию 60. |
| `--max-response-bytes <байты>` | Предел ответа API, который возвращается агенту, по умолчанию 262144 (256 КиБ). Больший ответ — ошибка с подсказкой сузить запрос. С [фильтром `jq`](tools.md#фильтр-ответа-jq) предел относится к результату фильтра. |
| `--log-level <уровень>` | Уровень или фильтр логов в stderr (`info`, `debug`, `rustore_mcp_core=debug`). Без флага — переменная `RUST_LOG`, без неё — `warn`. |
| `--status` | Показать действующие настройки и выйти, не запуская сервер. |

### Уровни доступа и наборы

Без настроек сервер работает только на чтение с наборами `apps`, `releases` и `reviews`. Права — из профиля ([Профили](#профили)): уровень доступа и каталоги `allow_path`. Флаги `--allow-write`, `--allow-destructive` и `--allow-path` права только сужают: флаг, который просит больше, чем разрешено в профиле, — ошибка запуска с подсказкой. На macOS права сверх одобренных отсекаются с предупреждением в stderr, сервер при этом запускается; так и регистрации старых версий с флагами доступа продолжают работать. Инструменты выше уровня не регистрируются; вызов такого инструмента объясняет, как поднять уровень.

Наборы: `--toolsets` важнее `toolsets` профиля, без `--dynamic-toolsets` действует настройка `dynamic_toolsets` профиля. Неизвестный набор — ошибка запуска со списком допустимых.

Каталоги для файлов: рабочий каталог сервера (если это не корень файловой системы и не домашний каталог), системный временный каталог и каталоги `allow_path` профиля ([Локальные файлы](security.md#локальные-файлы)).

Пользовательские инструменты читаются при запуске из `tools.toml` рядом с `profiles.toml`, если файл есть, и из файлов `--tools-file`. Ошибка в файле — ошибка запуска; проверить файлы заранее можно командой [`tools check`](#tools).

Что входит в уровни и наборы, как устроены аргументы и ответы инструментов, `api_search` и `api_request` — в [MCP-инструментах](tools.md). Вырезание учётных данных из ответов и правила для локальных файлов — в [Безопасности](security.md).

### serve --status

```text
rustore-mcp serve --status [--profile <имя>] [--allow-write] [--allow-destructive] [--toolsets ...]
                  [--dynamic-toolsets] [--tools-file <путь>]...
```

Печатает, с какими настройками запустился бы сервер с теми же флагами: профиль, ключ (замаскированный keyId и размер RSA, без значения), имена пакетов, уровень доступа и откуда он взят (флаги, профиль или по умолчанию), состояние одобрения (строка `Approval`, на macOS) и предупреждение, если права урезаны, наборы, включены ли динамические наборы, число инструментов, сколько пользовательских инструментов определено и зарегистрировано (и путь к `tools.toml`), разрешённые каталоги и путь к `profiles.toml`. Сервер не запускается, к API запросов нет. Флаг доступа сверх прав профиля — ошибка, как и у `serve`.

### serve --http

```text
rustore-mcp serve --http --access-tokens <файл> [--profile <имя> | --key-file <файл> [--key-id <ID>]]
                  [--push-file <файл>]
                  [--listen <IP:порт>] [--allowed-host <имя>]... [--allowed-origin <origin>]...
                  [--max-request-bytes <байты>] [--allow-write] [--allow-destructive]
                  [--toolsets <набор,...>|all] [--tools-file <путь>]... [--timeout <секунды>]
                  [--max-response-bytes <байты>] [--log-level <уровень>]
```

Запускает тот же сервер как HTTP-сервис (Streamable HTTP без сессий): `POST /mcp` и `GET /health`, по умолчанию на `127.0.0.1:8766`. Ключ RuStore API остаётся на сервере: из системного хранилища профиля `--profile` или из файла секрета `--key-file` (контейнеры). Клиенты MCP передают только свой токен доступа в `Authorization: Bearer <токен>`; в файле `--access-tokens` — SHA-256 каждого токена, его имя, уровень доступа и наборы. Флаги `--allow-write` и `--allow-destructive` задают потолок для токенов; права профиля и их одобрение к HTTP-режиму не относятся. Локальные файлы выключены; `--allow-path`, `--status` и `--dynamic-toolsets` вместе с `--http` — ошибка.

| Флаг | Назначение |
| --- | --- |
| `--http` | Режим HTTP вместо stdio. |
| `--access-tokens <файл>` | TOML с токенами доступа клиентов: обязателен. |
| `--key-file <файл>` | Файл секрета с ключом RuStore API вместо хранилища профиля: только Unix, обычный файл (или ссылка на него) с правами 0600 или 0400. |
| `--key-id <ID>` | keyId для `--key-file`, в котором только приватный ключ. |
| `--push-file <файл>` | Файл секрета с проектом и сервисным токеном push, JSON `{"projectId": ..., "serviceToken": ...}`, вместо хранилища профиля: только Unix, права 0600 или 0400. С `--key-file` push настраивается только им. |
| `--listen <IP:порт>` | Адрес и порт, по умолчанию `127.0.0.1:8766`. |
| `--allowed-host <имя>` | Дополнительное допустимое значение `Host` (`имя` или `имя:порт`); флаг повторяется. |
| `--allowed-origin <origin>` | Допустимый `Origin` браузерного клиента; флаг повторяется. |
| `--max-request-bytes <байты>` | Предел тела запроса MCP, по умолчанию 1048576 (1 МиБ). |

Файл токенов доступа:

```toml
[[tokens]]
name = "ci"                     # имя для логов: [A-Za-z0-9._-], до 64 символов
sha256 = "<64 hex-символа>"     # SHA-256 токена, сам токен в файле не хранится
access = "read"                 # read, write или destructive; не выше флагов сервера
toolsets = ["<набор>"]          # необязательно: наборы этого токена
```

Токен можно создать командой `openssl rand -hex 32`, его хеш — `printf %s "$TOKEN" | sha256sum`. Коды ответов, Docker-образ, `compose.yaml` и подключение клиентов — в [HTTP-режиме](http.md).

## auth

### auth login

```text
rustore-mcp auth login [--profile <имя>] [--key-file <файл> | --key-stdin] [--key-id <ID>]
                       [--package <имя>]... [--no-verify]
```

| Флаг | Назначение |
| --- | --- |
| `--key-file <файл>` | Файл ключа RuStore API ([форматы](#ключ-rustore-api)). Без флага и без `--key-stdin` путь спрашивается в терминале. |
| `--key-stdin` | Прочитать ключ из stdin (например, из менеджера паролей). Вопросов нет: keyId передайте в файле или флагом `--key-id`. |
| `--key-id <ID>` | keyId, если в файле только приватный ключ. |
| `--package <имя>` | Имя пакета приложения по умолчанию; флаг повторяется и заменяет список в профиле. |
| `--no-verify` | Сохранить ключ без проверки (без сети). |

Сохраняет ключ RuStore API профиля:

1. Ключ читается из файла, из stdin или по пути, который спрашивается в терминале; печатаются замаскированный keyId и размер RSA.
2. Проверка: сервер подписывает запрос токена и запрашивает список приложений `GET /public/v1/application`; печатается число приложений, доступных ключу. Отказ в токене (неверный keyId или ключ, ключ отключён) и отказ в доступе к методу (у ключа не отмечен метод или приложение) различаются в сообщении. `--no-verify` пропускает проверку.
3. Ключ сохраняется в системное хранилище, заменяя прежний; если проверка не прошла, ничего не сохраняется. Новый профиль создаётся с доступом только на чтение; `--package` записывает имена пакетов, остальные настройки профиля не меняются.
4. В терминале команда предлагает удалить исходный файл ключа (по умолчанию — нет).

### auth status

```text
rustore-mcp auth status [--profile <имя>] [--no-verify]
```

Показывает профиль, ключ (замаскированный keyId и размер RSA, без значения), результат проверки (`Check`: получение токена и запрос списка приложений; с `--no-verify` — без запроса), имена пакетов, клиент, в котором профиль зарегистрирован через `connect`, разрешены ли запись и удаление, наборы инструментов и путь к `profiles.toml`. Если проверка не прошла, причина печатается в строке `Check`.

Строка `Push` показывает, сохранены ли проект и сервисный токен push: идентификатор проекта в маске, без токена; токен не проверяется.

### auth logout

```text
rustore-mcp auth logout [--profile <имя>] [--forget]
```

Удаляет ключ профиля из системного хранилища. С `--forget` также удаляет настройки профиля из `profiles.toml`. Если ключ больше нигде не нужен, удалите его и в консоли RuStore («Компания → RuStore API»).

С `--forget` удаляются и проект и сервисный токен push профиля.

### auth push

```text
rustore-mcp auth push login [--profile <имя>] (--token-file <файл> | --token-stdin) [--project-id <ID>]
rustore-mcp auth push logout [--profile <имя>]
```

Сохраняет и удаляет второй, необязательный секрет профиля — учётные данные [Push API RuStore](tools.md#отправить-push-уведомление) для набора `push`: идентификатор проекта push и сервисный токен. Оба показаны в консоли RuStore: «Приложение → Push-уведомления → Проекты»; у проекта может быть до пяти сервисных токенов. Ключ RuStore API для Push API не подходит, а сервисный токен не уходит в RuStore API.

| Флаг | Назначение |
| --- | --- |
| `--token-file <файл>` | Файл с сервисным токеном или JSON `{"projectId": ..., "serviceToken": ...}`. В терминале команда затем предлагает удалить файл (по умолчанию — нет). |
| `--token-stdin` | Прочитать токен (или тот же JSON) из stdin. |
| `--project-id <ID>` | Идентификатор проекта push, если в файле только токен. |

Токен не принимается аргументом командной строки и не читается из переменных окружения. Он сохраняется в системное хранилище (учётная запись `<профиль>/push`), заменяя прежний, без проверки: любой запрос Push API отправляет уведомление или меняет подписки, поэтому проверьте токен отправкой на своё устройство. `logout` удаляет только учётные данные push; ключ RuStore API профиля остаётся.

### auth check

```text
rustore-mcp auth check [--profile <имя>] [--json]
```

Проверяет, что ключу профиля можно делать. Права ключа задаются в консоли RuStore («Компания → RuStore API») по методам и по приложениям, а методы и приложения, которые появились позже, в созданный ключ не добавляются: без проверки об отказе узнаёшь только при вызове инструмента.

1. Сервер получает токен (как `auth status`) и читает список приложений компании (`list_apps`, все страницы).
2. Для каждого раздела API — один безопасный запрос чтения с наименьшей страницей: версии (`list_versions`), скриншоты версии (`list_screenshots`), рейтинг (`get_app_rating`), платежи за сегодня (`list_payments_by_date`), подписка (`get_subscription_v5` с заведомо несуществующей покупкой: любой ответ, кроме `401` и `403`, значит, что метод разрешён), продукты каталога (`list_catalog_products`), доступы (`list_app_access`). Где разделу нужно приложение, берётся первое доступное; приложения проверяются по очереди, не больше 10. Если `list_apps` недоступен, проверяются пакеты профиля по умолчанию (`--package`), но без `appId` платежи и каталог остаются непроверенными.
3. Печатается таблица «раздел — статус — метод»: `available`, `denied` (с подсказкой, какой метод отметить у ключа; название метода — как в справочнике и в консоли), `not checked` (нет приложения, `appId` или версии) или `error`. Затем — приложения со статусом `accessible`, `denied` (ключу не выдано приложение: раздел, который работает для других приложений, для него отклонён) или `unknown` (отклонено всё, и ни один раздел нигде не ответил).

```text
Section        Status       Method (tool and its name in the RuStore console)
apps           available    list_apps "Получение списка приложений"
releases       available    list_versions "Получение статуса версий приложений"
purchases      denied       list_payments_by_date "Получение списка платежей за выбранную дату"
                            the method "Получение списка платежей за выбранную дату" is not ticked for the key: HTTP 403 …
…
Apps:      1 of 4 accessible
  com.example.app    accessible   Пример (appId 1234)
  com.example.other  denied       Другое (appId 5678)
                     `list_versions` works for other apps but is denied for this one: HTTP 403 …
```

Данные из ответов (версии, отзывы, платежи, пользователи) не печатаются. `--json` печатает тот же отчёт в JSON — его же возвращает MCP-инструмент [`auth_check`](tools.md#составные-инструменты). Код выхода не 0, только если проверить нельзя совсем: нет ключа, RuStore не выдал токен или API недоступен.

## key exec

```text
rustore-mcp key exec [--profile <имя>] [--env <ИМЯ>]... -- <команда> [аргументы...]
```

Запускает команду с ключом профиля во временном файле — для программ, которым нужен ключ RuStore API: Gradle-плагина публикации RuStore, fastlane, своих скриптов. Команды, которая печатает ключ, нет; `key exec` отдаёт его только дочерней команде.

- Ключ записывается в новый файл `rustore-credentials.json` с правами 0600 в новом временном каталоге с правами 0700. В Windows вместо режимов — ACL: доступ к каталогу и файлу только у текущего пользователя.
- Формат файла — JSON с полями `key_id` (keyId) и `client_secret` (приватный ключ строкой Base64, как его показывает консоль RuStore при создании ключа):

  ```json
  {
    "key_id": "…",
    "client_secret": "MIIE…"
  }
  ```

  Почему такой формат: это файл `credentialsPath` Gradle-плагина публикации RuStore (`ru.cian.rustore-publish-gradle-plugin`), его понимают без преобразования; в нём тот же Base64 DER PKCS#8, который ждут и плагины fastlane для RuStore (параметр `private_key`), и любой скрипт, который подписывает запрос токена сам; поля легко достать `jq -r .key_id` и `jq -r .client_secret`. Этот же файл принимают `auth login --key-file` и `serve --http --key-file`. В системном хранилище ключ лежит в том же виде, только с полями `keyId` и `privateKey`.
- Команда запускается без оболочки, stdin наследуется, путь к файлу и keyId передаются в переменных окружения:

| Переменная | Значение |
| --- | --- |
| `RUSTORE_KEY_FILE` | путь к файлу ключа |
| `RUSTORE_KEY_ID` | keyId ключа (его же читает fastlane-плагин RuStore) |

- `--env NAME` (повторяемый) кладёт путь в `NAME` вместо `RUSTORE_KEY_FILE`; тогда `RUSTORE_KEY_FILE` убирается из окружения команды, чтобы не указал на другой ключ.
- Сам приватный ключ в переменные окружения не попадает. Унаследованная `RUSTORE_PRIVATE_KEY` (содержимое ключа для fastlane-плагина) убирается, чтобы команда не взяла чужой ключ; если она нужна, задайте её из файла внутри дочерней оболочки.
- Аргументы команды не раскрываются: чтобы подставить переменную, запустите оболочку сами, в одинарных кавычках:

```bash
rustore-mcp key exec --profile work -- sh -c \
    './gradlew publishRustoreRelease --credentialsPath "$RUSTORE_KEY_FILE"'
rustore-mcp key exec --profile work -- sh -c \
    'RUSTORE_PRIVATE_KEY="$(jq -r .client_secret "$RUSTORE_KEY_FILE")" fastlane android rustore'
rustore-mcp key exec --profile work --env CREDENTIALS_PATH -- ./scripts/upload.sh
```

- В stdout и stderr команды на `***` заменяются ключ (весь файл, приватный ключ целиком, по строкам PEM и в base64), keyId и токены RuStore (JWE, `eyJ…`). Это страховка от случайного вывода, а не граница безопасности: не выводите ключ.
- Файл и каталог удаляются после завершения команды — и при ошибке, и при ненулевом коде, и при прерывании: Ctrl-C команда получает от терминала, SIGTERM и SIGHUP пересылаются ей. От принудительного завершения (`kill -9`) защиты нет: тогда каталог останется во временном каталоге пользователя.
- В Windows Ctrl+C и Ctrl+Break команда получает от консоли сама. Команда и запущенные ею процессы работают в объекте задания: когда команда завершилась или закрывается окно консоли (выход из системы, выключение), оставшиеся процессы останавливаются и файл удаляется. Команда без расширения ищется и как `.cmd` и `.bat` (`gradlew` → `gradlew.bat`). Переменные в аргументах подставляет оболочка, которую вы запустите сами, например PowerShell (пример — для запуска из PowerShell: одинарные кавычки не дают внешней оболочке подставить переменную раньше времени):

```powershell
rustore-mcp key exec --profile work -- powershell -NoProfile -Command '.\gradlew.bat publishRustoreRelease --credentialsPath $env:RUSTORE_KEY_FILE'
```

- Код завершения — код команды (при завершении сигналом в Unix — 128 + номер сигнала).

## tools

```text
rustore-mcp tools list [--tools-file <путь>]...
rustore-mcp tools check [--tools-file <путь>]...
```

Работают с [пользовательскими инструментами](tools.md#пользовательские-инструменты). Файл пользователя `tools.toml` рядом с `profiles.toml` читается всегда, если он есть; `--tools-file` добавляет те же файлы, что и у `serve`. К API команды не обращаются, ключ не нужен.

- `tools list` печатает таблицу: имя, уровень доступа, операция, фиксированные аргументы, есть ли фильтр `jq`, файл. Инструменты выше уровня доступа сервера при запуске не регистрируются.
- `tools check` проверяет файлы так же, как `serve` при запуске (TOML, поля, операции, фиксированные аргументы по схеме операции, фильтры `jq`, совпадения имён), и печатает для каждого файла `OK` и число инструментов. Ошибка — код выхода не 0 и сообщение с файлом и инструментом.

## call

Вызывает инструмент сервера из консоли.

```text
rustore-mcp call [--profile <имя>] [--allow-write] [--allow-destructive]
    [--allow-path <каталог>]... [--toolsets <набор,...>] [--tools-file <путь>]...
    [--timeout <секунды>] [--max-response-bytes <байты>]
    [<инструмент> [<имя>=<значение> | <имя>:=<JSON>]... [--args <JSON>|-] [--schema] [--yes] [--raw]]
```

- Без инструмента печатает инструменты, доступные профилю, с уровнем доступа и первой строкой описания. `--schema` печатает схему аргументов инструмента.
- Сервер собирается как stdio-сервер `serve` без флагов: права профиля (на macOS — одобренные), флаги только сужают. По умолчанию включены все наборы (`--toolsets` сужает), наборов по запросу нет. Клиент MCP работает в этом же процессе, поэтому проверка аргументов, уровни доступа, фильтр `jq` и вырезание секретов те же, что у агента.
- Аргументы: `имя=значение` — тип берётся из схемы инструмента (числа, логические значения, JSON-массивы и объекты; для массива строк — список через запятую), `имя:=JSON` — всегда JSON, `--args` — все аргументы одним JSON-объектом (`-` — из stdin). Флаги команды пишутся до имени инструмента.
- Инструменты уровня удаления спрашивают подтверждение в терминале; `--yes` — без вопроса, без терминала вызов отклоняется.
- Результат: текстовые блоки (JSON — с отступами); `--raw` — ответ MCP целиком. Код выхода — 0, если инструмент выполнился, и 1, если он вернул ошибку (`isError`) или вызов не удался.

```bash
rustore-mcp call list_apps pageSize=5
rustore-mcp call api_request method=GET path=/public/v1/application jq='[.content[].packageName]'
rustore-mcp call --profile partner reviews_summary --args '{"packageName": "com.example.app", "days": 7}'
```

## ui

Интерактивный просмотр профилей в терминале.

```text
rustore-mcp ui
```

Вкладки:

- **Profile** — настройки профиля и состояние ключа: замаскированный keyId и размер ключа (сам ключ не показывается), учётные данные push, имена пакетов, наборы.
- **Access** — права профиля и их одобрение. `r`, `w`, `d` — уровень, `a` — добавить каталог, `x` — убрать, `u` — отменить, `s` — сохранить. На macOS сохранение прав шире одобренных спрашивает Touch ID или пароль пользователя macOS.
- **Clients** — регистрации сервера в Claude Code (`~/.claude.json`, `.mcp.json` текущего каталога) и Codex (`$CODEX_HOME/config.toml`): профиль, флаги и расхождения с правами профиля. `f` регистрирует запись заново без флагов доступа (записи HTTP-режима не трогаются). Значения переменных окружения записей не читаются.
- **Account** — что разрешено ключу в RuStore (`c` — проверить): тот же отчёт, что [`auth check`](#auth-check), — доступность разделов API и приложений по пробным запросам чтения. Сами права ключа (методы и приложения) отмечаются в консоли RuStore («Компания → RuStore API») и через API не читаются.
- **Tools** — инструменты, которые профиль даёт агенту (`c` — загрузить), `Enter` — вызвать с аргументами `имя=значение`, `?` — схема.

`q` или `Esc` — выход, `Tab` и `1`–`5` — вкладки, `F5` — перечитать. Без терминала (агент, CI) команда завершается ошибкой.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `RUSTORE_MCP_CONFIG_DIR` | Каталог с `profiles.toml` и `tools.toml` вместо `~/.config/rustore-mcp`. |
| `CODEX_HOME` | Каталог конфигурации Codex для `connect codex` вместо `~/.codex`. |
| `RUST_LOG` | Уровень логов `serve` в stderr, если не задан `--log-level`. |

Ключ RuStore API из переменных окружения не читается никогда.
