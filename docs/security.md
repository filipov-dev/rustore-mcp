# Безопасность

Сервер даёт агенту доступ к RuStore API от имени ключа компании. Ниже — какие границы держит сам сервер и что остаётся на стороне пользователя.

## Ключ RuStore API

- Ключ (keyId и приватный ключ RSA) создаёт владелец или администратор компании в консоли RuStore («Компания → RuStore API»). Права ключа задаются там же: методы API и приложения, с которыми он может работать. Агенту, которому достаточно чтения, давайте ключ только с методами чтения.
- Ключ хранится только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Запись: сервис `dev.filipov.rustore-mcp`, учётная запись — имя профиля.
- Ключ принимается только из файла (`--key-file` или путь, который спрашивается в терминале) или из stdin (`auth login --key-stdin`). Он не принимается аргументом командной строки и не читается из переменных окружения или `.env`. Файл ключа больше 16 КиБ и ключ RSA короче 2048 бит отклоняются; текст ошибки разбора не содержит фрагментов ключа.
- Ни одна команда не печатает ключ и токен: `auth status` и `serve --status` показывают только замаскированный keyId (первые и последние четыре символа) и размер ключа. После сохранения `connect` и `auth login` в терминале предлагают удалить исходный файл ключа (по умолчанию — нет).
- В конфигурацию MCP-клиента попадает только команда `rustore-mcp serve --profile <профиль> …`, в `profiles.toml` — настройки профиля без ключа.
- Ключа и токена нет в аргументах инструментов. Заголовок `Public-Token` добавляет сервер, и `api_request` не может его переопределить; пути `api_request` — только относительные пути RuStore API из спецификации.
- Один ключ компании — один профиль. Ключ, который больше не нужен, удалите и в хранилище (`auth logout`), и в консоли RuStore.

### Токен RuStore API

- Сервер получает токен (JWE) запросом `POST /public/auth/` с keyId, временем и подписью SHA512withRSA; подпись вычисляется в процессе, приватный ключ никуда не отправляется.
- Токен живёт только в памяти процесса сервера: не пишется в системное хранилище, `profiles.toml` и другие файлы, не печатается командами и не попадает в логи. Сервер обновляет его до истечения срока, а после ответа `401` один раз повторяет запрос с новым токеном.
- Токен уходит только в RuStore API (`https://public-api-m.rustore.ru`) и вырезается из любого текста, который получает агент. Редиректы на другие хосты не выполняются.

В [HTTP-режиме](http.md) ключ остаётся на сервере: из хранилища профиля или из файла секрета `--key-file` с правами `0600` или `0400` (только Unix, для контейнеров). Клиенты присылают только свой токен доступа к MCP; сервер хранит лишь SHA-256 токенов, сравнивает их за постоянное время и не пишет ни токены, ни их хеши в логи.

## Уровни доступа

По умолчанию сервер работает только на чтение. Запись (`--allow-write`) и удаление (`--allow-destructive`) включает пользователь при запуске сервера или в `connect`. Инструменты выше разрешённого уровня не регистрируются, а `api_request` не отправляет запросы выше уровня сервера.

Уровень записи — изменения черновика версии, которые пользователи RuStore не видят до модерации и публикации: создание и удаление черновика, его тексты и настройки, загрузка APK и AAB, иконка и скриншоты (`upload_build`, `listing_apply`, `sync_screenshots`).

Уровень удаления, кроме самих удалений (`DELETE`), получают действия с последствиями для пользователей RuStore и денег, даже если в API это `POST`, `PUT` или `PATCH`:

- отправка черновика на модерацию (`submit_draft_for_moderation`, `release_submit`): при автоматической публикации одобренная версия сразу уходит пользователям;
- ручная публикация версии (`publish_version`) и смена процента раскатки, типа и времени публикации (`update_publish_settings`; оба — через `release_rollout`);
- архивирование версии (`archive_version`);
- публичные ответы на отзывы, их изменение и удаление (`reply_to_review`, `update_review_answer`, `delete_review_answer`);
- возвраты платежей (`refund_payment`), отмены и подтверждения покупок (`cancel_purchase`, `confirm_purchase`), отмены и подтверждения подписок (`cancel_subscription`, `acknowledge_subscription`), в том числе в песочнице (`*_sandbox`);
- выдача и отзыв доступов к приложению (`grant_app_access`, `revoke_app_access`).

Уровень каждой операции записан в спецификации (`x-access-level`), `api_search` показывает его в результатах. Агенту в инструкциях сервера сказано подтверждать такие вызовы у пользователя, если тот не попросил о них явно; у `release_submit` и `release_rollout` есть пробный прогон `dry_run: true`.

Уровень доступа сервера не заменяет права ключа: RuStore проверяет методы и приложения, отмеченные у ключа. Сервер только сужает то, что агент может сделать с этим ключом.

## Учётные данные в ответах

Агенту не нужны ключи, токены и пароли, а из его контекста они легко попадают в логи, коммиты и документацию. Поэтому во всех ответах — успешных и ошибках, JSON и текстовых — сервер заменяет на `[redacted]` и добавляет к результату пометку об этом:

- строковые значения полей, имя которых похоже на учётные данные, на любой глубине: `password`, `passwd`, `pwd`, `passphrase`, `secret`, `token`, `jwe`, `jwt`, `privateKey`, `apiKey`, `clientSecret`, `credentials`, `signature`, `authorization`, `cookie`, в том числе в составе имени (`serviceToken`, `Public-Token`, `db_password`);
- значения, похожие на секрет по форме, в любом тексте, включая описания приложений и комментарии к версиям: приватные ключи RSA в PEM и в Base64 (DER), токены JWE и JWT, значения после `Public-Token`, `Bearer` и `Basic`, пароль в URL (`https://user:пароль@host`); остальной текст остаётся.

Не скрываются признаки вида `has_password` и `isSecret`, пустые строки, идентификаторы постраничной выдачи и поля платежей `purchaseToken`, `subscriptionToken` и `invoiceId`: это не секреты доступа, а идентификаторы, по которым агент проверяет покупку или подписку.

В инструкциях сервера агенту сказано не просить ключи и токены в чате и не пытаться восстановить скрытые значения.

## Фильтр jq

[Фильтр `jq`](tools.md#фильтр-ответа-jq) применяется после замены учётных данных и вырезания токена сервера: он получает очищенный ответ и не может раскрыть скрытые значения ни выборкой, ни преобразованием (`.. | strings`, `tojson`, `@base64d`). Фильтру недоступны окружение процесса, входные потоки и модули. Он выполняется в отдельном процессе того же бинарника с пустым окружением: ему недоступны переменные окружения, системное хранилище ключей и профили, а зависание или переполнение стека завершают только этот процесс (таймаут — 10 секунд). Лимит `--max-response-bytes` действует для результата фильтра.

## Пользовательские инструменты

[Пользовательские инструменты](tools.md#пользовательские-инструменты) вызывают обычные операции API через те же проверки, что и встроенные инструменты: схема аргументов операции, уровень доступа операции, замена учётных данных в ответе. Заголовков, полных URL и произвольных путей в описании инструмента нет. Фиксированные аргументы агент переопределить не может; `save_to` и файловые аргументы фиксировать нельзя, поэтому правила для локальных файлов действуют и здесь.

Файлы инструментов — доверенная конфигурация пользователя. Автоматически читается только `tools.toml` в каталоге конфигурации рядом с `profiles.toml`; другие файлы подключаются только явным `--tools-file`, поэтому файл из клонированного репозитория сам по себе ничего не добавляет. Имя, совпадающее со встроенным инструментом, — ошибка запуска, а не подмена. В HTTP-режиме файлы инструментов читает только сервер при запуске (агенты их не передают), вызовы идут с токеном агента из запроса, а инструменты над операциями с локальными файлами не регистрируются.

## Локальные файлы

Чтение локальных файлов (аргумент `file` у `upload_apk`, `upload_aab`, `upload_icon` и `upload_screenshot*`, сборки `upload_build`, каталог `dir` у `listing_apply` и `sync_screenshots`) и запись (аргумент `save_to` у инструментов, которые возвращают файл, например `export_reviews_csv`, и у `api_request` для таких операций, `save_to` у `reviews_export` и `payments_report`, каталог `dir` у `listing_export`) работают только с путями внутри разрешённых каталогов:

- рабочий каталог сервера, если это не корень файловой системы и не домашний каталог;
- системный временный каталог: он разрешён для черновых файлов и скачивания во временные файлы, но общий для всех программ пользователя, поэтому не держите в нём ничего личного;
- каталоги из `--allow-path`.

Пути проверяются после раскрытия `..` и символических ссылок: файл или каталог, который ссылкой ведёт за пределы разрешённых каталогов, отклоняется и при загрузке, и при скачивании (в том числе каталог назначения `save_to`). Относительный путь считается от рабочего каталога сервера. `save_to` указывает на новый файл: существующие файлы и символические ссылки не перезаписываются. Файл открывается по проверенному пути, после открытия сервер сверяет, что путь не подменили (например, заменой каталога на ссылку между проверкой и открытием); при подмене файл не отправляется и ответ в него не записывается.

## Протокол и логи

- stdout занят протоколом MCP; логи и диагностика пишутся только в stderr. Уровень — `--log-level`, иначе `RUST_LOG`, иначе `warn`. Ключ, токен RuStore API и токены доступа HTTP-режима в логи не попадают.
- Ошибки RuStore API (`4xx`, `5xx`) и запрещённые вызовы возвращаются агенту как результат инструмента с `isError: true`; процесс не падает.
- stdio-сервер не открывает сетевых портов и ходит только в RuStore API. Редиректы на другие хосты не выполняются.
- HTTP-сервер (`serve --http`) по умолчанию слушает только `127.0.0.1`, проверяет `Host` и `Origin` (защита от DNS rebinding) и без токена отвечает `401`. Снаружи loopback его нужно закрывать TLS ([HTTP-режим](http.md#за-reverse-proxy-с-tls)).
