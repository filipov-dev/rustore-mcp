# Безопасность

Сервер даёт агенту доступ к RuStore API от имени ключа компании. Ниже — какие границы держит сам сервер и что остаётся на стороне пользователя.

## Ключ RuStore API

- Ключ (keyId и приватный ключ RSA) создаёт владелец или администратор компании в консоли RuStore («Компания → RuStore API»). Права ключа задаются там же: методы API и приложения, с которыми он может работать. Агенту, которому достаточно чтения, давайте ключ только с методами чтения.
- Ключ хранится только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Запись: сервис `dev.filipov.rustore-mcp`, учётная запись — имя профиля.
- Ключ принимается только из файла (`--key-file` или путь, который спрашивается в терминале) или из stdin (`auth login --key-stdin`). Он не принимается аргументом командной строки и не читается из переменных окружения или `.env`. Файл ключа больше 16 КиБ и ключ RSA короче 2048 бит отклоняются; текст ошибки разбора не содержит фрагментов ключа.
- Ни одна команда не печатает ключ и токен: `auth status` и `serve --status` показывают только замаскированный keyId (первые и последние четыре символа) и размер ключа. После сохранения `connect` и `auth login` в терминале предлагают удалить исходный файл ключа (по умолчанию — нет).
- В конфигурацию MCP-клиента попадает только команда `rustore-mcp serve --profile <профиль> …`, в `profiles.toml` — настройки профиля без ключа.
- Ключа и токена нет в аргументах инструментов. Заголовок `Public-Token` добавляет сервер, и `api_request` не может его переопределить; пути `api_request` — только относительные пути RuStore API из спецификации.
- Один ключ компании — один профиль. Ключ, который больше не нужен, удалите и в хранилище (`auth logout`), и в консоли RuStore.

### Токен RuStore API

- Сервер получает токен (JWE) запросом `POST /public/auth/` с keyId, временем и подписью SHA512withRSA; подпись вычисляется в процессе, приватный ключ никуда не отправляется.
- Токен живёт только в памяти процесса сервера: не пишется в системное хранилище, `profiles.toml` и другие файлы, не печатается командами и не попадает в логи. Сервер обновляет его до истечения срока, а после ответа `401` один раз повторяет запрос с новым токеном.
- Токен уходит только в RuStore API (`https://public-api-m.rustore.ru`) и вырезается из любого текста, который получает агент. Редиректы на другие хосты не выполняются.

В [HTTP-режиме](http.md) ключ остаётся на сервере: из хранилища профиля или из файла секрета `--key-file` с правами `0600` или `0400` (только Unix, для контейнеров). Клиенты присылают только свой токен доступа к MCP; сервер хранит лишь SHA-256 токенов, сравнивает их за постоянное время и не пишет ни токены, ни их хеши в логи.

### Права ключа

Методы и приложения ключа видит только RuStore: сервер их не знает и не расширяет. `rustore-mcp auth check` (инструмент `auth_check`) проверяет их запросами только на чтение, по одному на раздел, и не показывает данных из ответов; ошибка `401` или `403` инструмента называет метод и приложение, которые нужно отметить у ключа в консоли.

### key exec

Gradle-плагину публикации RuStore, fastlane и скриптам нужен сам ключ. `rustore-mcp key exec -- <команда>` отдаёт его дочерней команде, не показывая:

- ключ пишется в новый файл `rustore-credentials.json` (JSON `key_id` и `client_secret`, формат Gradle-плагина) с правами 0600 в новом временном каталоге с правами 0700; в Windows вместо режимов у каталога отключается наследование прав и остаётся одна запись ACL — полный доступ текущего пользователя (по SID), а файл создаётся уже после этого и получает те же права. В окружение команды попадают путь к файлу (`RUSTORE_KEY_FILE` или имена из `--env`) и keyId (`RUSTORE_KEY_ID`), но не приватный ключ; унаследованная `RUSTORE_PRIVATE_KEY` убирается;
- команда запускается без оболочки, её stdout и stderr проходят через маскировщик: файл ключа, приватный ключ целиком, строками PEM и в base64, keyId и токены JWE заменяются на `***`. Это страховка от случайного вывода, а не граница безопасности;
- файл и каталог удаляются после завершения команды при любом исходе, в том числе при Ctrl-C, SIGTERM и SIGHUP. От `kill -9` защиты нет: тогда каталог останется во временном каталоге пользователя, доступный только ему;
- в Windows команда и запущенные ею процессы работают в объекте задания (Job Object): когда команда завершилась, закрывается окно консоли или завершается сеанс, оставшиеся процессы останавливаются, чтобы файл ключа никто не держал открытым, и файл удаляется (занятый антивирусом файл удаляется с несколькими повторами).

Агент с доступом к оболочке на той же машине может запустить `key exec` от имени пользователя: это граница доверия к агенту, а не к серверу. Подробнее — [справочник CLI](cli.md#key-exec).

## Сервисный токен push

Набор `push` (выключен по умолчанию) отправляет push-уведомления через Push API RuStore. Для него у профиля есть второй, необязательный секрет: идентификатор проекта push и сервисный токен из консоли RuStore («Приложение → Push-уведомления → Проекты»).

- Проект и сервисный токен хранятся только в системном хранилище, отдельно от ключа RuStore API: сервис `dev.filipov.rustore-mcp`, учётная запись `<профиль>/push`. Сохраняет их `auth push login`, удаляет `auth push logout` (и `auth logout --forget` вместе с профилем).
- Токен принимается только из файла (`--token-file`) или из stdin (`--token-stdin`), не аргументом командной строки и не из переменных окружения. `auth status` и `serve --status` показывают только, настроен ли push, и идентификатор проекта в маске; токен не печатается.
- Сервисный токен уходит только на хосты Push API (`https://vkpns.rustore.ru` и `https://vkpns-topics.rustore.ru`) в заголовке `Authorization: Bearer` и никогда — в RuStore API (`public-api-m.rustore.ru`). Токен RuStore API, в свою очередь, не уходит на хосты push. `api_request` ходит только в RuStore API и вызвать Push API не может.
- Push-токены устройств из запроса и ответа (`token`, `push_token`, `push_tokens`) скрываются в ответах и ошибках так же, как учётные данные.
- Сообщение больше 4096 байт отклоняется до отправки.
- В HTTP-режиме проект и токен берутся из хранилища профиля или из файла секрета `--push-file` (JSON `{"projectId", "serviceToken"}`, права `0600` или `0400`, только Unix). С `--key-file` без `--push-file` набор `push` не настроен.
- Проверить токен без отправки нельзя: в Push API нет безопасного запроса на чтение. `auth push login` сохраняет токен без проверки; проверьте его отправкой на своё устройство.
## Уровни доступа

По умолчанию сервер работает только на чтение. Запись (`allow_write` в профиле) и удаление (`allow_destructive`, включает и запись) включает пользователь в `rustore-mcp ui` или в `connect --allow-write`/`--allow-destructive`. Инструменты выше разрешённого уровня не регистрируются, а `api_request` не отправляет запросы выше уровня сервера.

- Уровень доступа и каталоги `allow_path` — настройки профиля, а не регистрации в клиенте. Клиент запускает `serve --profile <имя>` без флагов доступа; флаги `serve` (`--allow-write`, `--allow-destructive`, `--allow-path`) права только сужают, а флаг, который просит больше профиля, — ошибка запуска. Поэтому правка конфигурации клиента (`~/.claude.json`, `.mcp.json`, `config.toml` Codex) прав не повышает. Регистрации старых версий с флагами доступа запускаются, пока флаги не выходят за права профиля.
- На macOS права сверх чтения действуют только после одобрения владельцем. `rustore-mcp ui` и `connect` при повышении прав спрашивают Touch ID или пароль пользователя macOS и кладут одобренную копию прав в Keychain (сервис `rustore-mcp.access`, учётная запись — имя профиля). При запуске сервер сверяет права из `profiles.toml` с одобренными: если в файле больше, чем одобрено (например, файл правили вручную), сервер работает в пределах одобренного, а без одобрения — только на чтение, и пишет предупреждение в stderr. `serve --status` показывает состояние одобрения в строке `Approval`.
- В Linux и Windows одобрения нет: системное хранилище там не привязывает записи к приложению, и любой процесс пользователя может их прочитать и изменить. Там права профиля действуют как записаны, а реальную границу задают права ключа в консоли RuStore («Компания → RuStore API»): методы и приложения, отмеченные для ключа. Для агента, которому нужно только чтение, создайте ключ без методов записи.
- В [HTTP-режиме](http.md) права профиля и одобрение не применяются: уровень сервера задают флаги `serve --http`, и он — потолок для токенов.

Уровень записи — изменения черновика версии, которые пользователи RuStore не видят до модерации и публикации: создание и удаление черновика, его тексты и настройки, загрузка APK и AAB, иконка и скриншоты (`upload_build`, `listing_apply`, `sync_screenshots`).

Уровень удаления, кроме самих удалений (`DELETE`), получают действия с последствиями для пользователей RuStore и денег, даже если в API это `POST`, `PUT` или `PATCH`:

- отправка черновика на модерацию (`submit_draft_for_moderation`, `release_submit`): при автоматической публикации одобренная версия сразу уходит пользователям;
- ручная публикация версии (`publish_version`) и смена процента раскатки, типа и времени публикации (`update_publish_settings`; оба — через `release_rollout`);
- архивирование версии (`archive_version`);
- публичные ответы на отзывы, их изменение и удаление (`reply_to_review`, `update_review_answer`, `delete_review_answer`);
- возвраты платежей (`refund_payment`), отмены и подтверждения покупок (`cancel_purchase`, `confirm_purchase`), отмены и подтверждения подписок (`cancel_subscription`, `acknowledge_subscription`), в том числе в песочнице (`*_sandbox`);
- выдача и отзыв доступов к приложению (`grant_app_access`, `revoke_app_access`, `access_apply`);
- отправка push-уведомлений на устройство и в топик (`send_push_notification`, `send_push_to_topic`): уведомление сразу приходит людям. Подписка и отписка устройств от топика (`subscribe_to_push_topic`, `unsubscribe_from_push_topic`) — уровень записи.

Уровень каждой операции записан в спецификации (`x-access-level`), `api_search` показывает его в результатах. Агенту в инструкциях сервера сказано подтверждать такие вызовы у пользователя, если тот не попросил о них явно; у `release_submit` и `release_rollout` есть пробный прогон `dry_run: true`.

### Доступы пользователей

`access_apply` меняет роль одного пользователя сразу в нескольких приложениях, поэтому у него есть дополнительные ограничения:

- роли владельца (`OWNER`, `NON_RESIDENT_OWNER`, `INDIVIDUAL_OWNER`) не выдаются и не отзываются: такой вызов отклоняется до запросов к API, владельца приложения меняют только в консоли RuStore;
- в приложениях, где пользователь — владелец, его доступ не меняется (запись `skip`);
- перед изменением читается текущий доступ каждого приложения, а `dry_run: true` возвращает план и не отправляет запросов записи; агенту сказано показать план пользователю и получить подтверждение;
- ошибка по одному приложению (например, 403, если ключу не выдано это приложение) записывается в его строку результата и не останавливает остальные.

Ответы `access_summary` и `list_app_access` содержат имена и VK ID людей. Агенту сказано не переносить их в логи, коммиты и Wiki; сам сервер их в логи не пишет: в путях запросов VK ID заменяется на `{devVkId}`, а в сообщениях ошибок составных инструментов его нет.

Уровень доступа сервера не заменяет права ключа: RuStore проверяет методы и приложения, отмеченные у ключа. Сервер только сужает то, что агент может сделать с этим ключом.

## Учётные данные в ответах

Агенту не нужны ключи, токены и пароли, а из его контекста они легко попадают в логи, коммиты и документацию. Поэтому во всех ответах — успешных и ошибках, JSON и текстовых — сервер заменяет на `[redacted]` и добавляет к результату пометку об этом:

- строковые значения полей, имя которых похоже на учётные данные, на любой глубине: `password`, `passwd`, `pwd`, `passphrase`, `secret`, `token`, `jwe`, `jwt`, `privateKey`, `apiKey`, `clientSecret`, `credentials`, `signature`, `authorization`, `cookie`, в том числе в составе имени (`serviceToken`, `Public-Token`, `db_password`);
- значения, похожие на секрет по форме, в любом тексте, включая описания приложений и комментарии к версиям: приватные ключи RSA в PEM и в Base64 (DER), токены JWE и JWT, значения после `Public-Token`, `Bearer` и `Basic`, пароль в URL (`https://user:пароль@host`); остальной текст остаётся;
- значения параметров query с учётными данными в ссылках (`?token=…`, `access_token`, `signature`, `X-Amz-Signature`, `sig`, `key`, `X-Goog-Credential` и т. п.): имя параметра и остальная ссылка остаются.

Не скрываются признаки вида `has_password` и `isSecret`, пустые строки, идентификаторы постраничной выдачи и поля платежей `purchaseToken`, `subscriptionToken` и `invoiceId`: это не секреты доступа, а идентификаторы, по которым агент проверяет покупку или подписку.

В инструкциях сервера агенту сказано не просить ключи и токены в чате и не пытаться восстановить скрытые значения.

## Фильтр jq

[Фильтр `jq`](tools.md#фильтр-ответа-jq) применяется после замены учётных данных и вырезания токена сервера: он получает очищенный ответ и не может раскрыть скрытые значения ни выборкой, ни преобразованием (`.. | strings`, `tojson`, `@base64d`). Фильтру недоступны окружение процесса, входные потоки и модули. Он выполняется в отдельном процессе того же бинарника с пустым окружением: ему недоступны переменные окружения, системное хранилище ключей и профили, а зависание или переполнение стека завершают только этот процесс (таймаут — 10 секунд). Лимит `--max-response-bytes` действует для результата фильтра.

## Пользовательские инструменты

[Пользовательские инструменты](tools.md#пользовательские-инструменты) вызывают обычные операции API через те же проверки, что и встроенные инструменты: схема аргументов операции, уровень доступа операции, замена учётных данных в ответе. Заголовков, полных URL и произвольных путей в описании инструмента нет. Фиксированные аргументы агент переопределить не может; `save_to` и файловые аргументы фиксировать нельзя, поэтому правила для локальных файлов действуют и здесь.

Файлы инструментов — доверенная конфигурация пользователя. Автоматически читается только `tools.toml` в каталоге конфигурации рядом с `profiles.toml`; другие файлы подключаются только явным `--tools-file`, поэтому файл из клонированного репозитория сам по себе ничего не добавляет. Имя, совпадающее со встроенным инструментом, — ошибка запуска, а не подмена. В HTTP-режиме файлы инструментов читает только сервер при запуске (агенты их не передают), вызовы идут с токеном агента из запроса, а инструменты над операциями с локальными файлами не регистрируются.

## Локальные файлы

Чтение локальных файлов (аргумент `file` у `upload_apk`, `upload_aab`, `upload_icon` и `upload_screenshot*`, сборки `upload_build`, каталог `dir` у `listing_apply` и `sync_screenshots`, каталог экспорта Google Play `play_dir` у `listing_apply`) и запись (аргумент `save_to` у инструментов, которые возвращают файл, например `export_reviews_csv`, и у `api_request` для таких операций, `save_to` у `reviews_export`, `payments_report` и `catalog_summary`, каталог `dir` у `listing_export`) работают только с путями внутри разрешённых каталогов:

- рабочий каталог сервера, если это не корень файловой системы и не домашний каталог;
- системный временный каталог: он разрешён для черновых файлов и скачивания во временные файлы, но общий для всех программ пользователя, поэтому не держите в нём ничего личного;
- каталоги `allow_path` профиля (на macOS — одобренные); `serve --allow-path` оставляет из них только указанные.

Пути проверяются после раскрытия `..` и символических ссылок: файл или каталог, который ссылкой ведёт за пределы разрешённых каталогов, отклоняется и при загрузке, и при скачивании (в том числе каталог назначения `save_to`). Относительный путь считается от рабочего каталога сервера. `save_to` указывает на новый файл: существующие файлы и символические ссылки не перезаписываются. Файл открывается по проверенному пути, после открытия сервер сверяет, что путь не подменили (например, заменой каталога на ссылку между проверкой и открытием); при подмене файл не отправляется и ответ в него не записывается.

## Файлы хранилища RuStore

RuStore API отдаёт иконку и скриншоты версии ссылками на своё хранилище (`iconUrl`, `fileUrl` на `static.rustore.ru`), а не путями API. Исполнитель запросов такие адреса не принимает, поэтому `listing_export` скачивает их отдельным клиентом с жёсткими правилами:

- только `https` на стандартном порту и только хосты из белого списка — сейчас один `static.rustore.ru`, точное совпадение имени, без поддоменов; другой хост, `http` и логин или пароль в адресе отклоняются до запроса;
- без токена RuStore API, заголовка `Authorization` и cookie: клиент о них не знает;
- редирект выполняется, только если новый адрес проходит те же проверки (не больше пяти); редирект на другой хост или на `http` не выполняется и становится ошибкой;
- файл не больше 10 МБ, таймаут — 60 секунд на файл; ответ, который не похож на PNG или JPEG, не сохраняется;
- файлы пишутся только в каталог `dir` внутри разрешённых каталогов, как новые: существующие файлы не перезаписываются;
- ссылка не попадает в ошибки и логи (там только хост), а в ответ агенту и в `images.json` — без query и fragment: если когда-нибудь ссылки станут подписанными, подпись останется у сервера.

Скачивание работает только с локальными файлами, поэтому в HTTP-режиме его нет.

## Протокол и логи

- stdout занят протоколом MCP; логи и диагностика пишутся только в stderr. Уровень — `--log-level`, иначе `RUST_LOG`, иначе `warn`. Ключ, токен RuStore API и токены доступа HTTP-режима в логи не попадают.
- Ошибки RuStore API (`4xx`, `5xx`) и запрещённые вызовы возвращаются агенту как результат инструмента с `isError: true`; процесс не падает.
- stdio-сервер не открывает сетевых портов и ходит только в RuStore API, с настроенным push — ещё в Push API RuStore, а для скачивания иконки и скриншотов в `listing_export`, в [хранилище RuStore](#файлы-хранилища-rustore). Редиректы на другие хосты не выполняются.
- Сервисный токен push и push-токены устройств в логи не попадают.
- HTTP-сервер (`serve --http`) по умолчанию слушает только `127.0.0.1`, проверяет `Host` и `Origin` (защита от DNS rebinding) и без токена отвечает `401`. Снаружи loopback его нужно закрывать TLS ([HTTP-режим](http.md#за-reverse-proxy-с-tls)).
