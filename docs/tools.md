# MCP-инструменты

Каждая операция RuStore API из встроенной спецификации — отдельный MCP-инструмент. Спецификация собрана из [справочника RuStore API](https://www.rustore.ru/help/work-with-rustore-api) и покрывает его методы: 49 операций в 8 наборах, в том числе варианты методов платежей и подписок для песочницы (`*_sandbox`). Имя инструмента — `operationId` операции в snake_case (`list_versions`, `create_draft_version`, `reply_to_review`), описание — из справочника и заканчивается ссылкой на его страницу. Поверх операций есть 11 [составных инструментов](#составные-инструменты) для частых задач (выпуск версии, тексты и скриншоты, отзывы, платежи), а всегда доступны `api_search` и `api_request`.

Какие инструменты видит агент, задают уровень доступа (`--allow-write`, `--allow-destructive`) и наборы (`--toolsets`) сервера. Со значениями по умолчанию — только чтение и наборы `apps`, `releases`, `reviews` — это 8 инструментов операций; с `--allow-write` — 13, с `--allow-destructive` — 20. Со всеми наборами — 21, 30 и 49.

## Уровни доступа

По умолчанию сервер работает только на чтение. Инструменты выше разрешённого уровня не регистрируются: агент их не видит, а вызов по имени возвращает ошибку с флагом, который их включает.

| Уровень | Как включить | Инструменты |
| --- | --- | --- |
| read-only | по умолчанию | только чтение: приложения, версии, отзывы и рейтинг, платежи, подписки, каталог, доступы |
| write | `--allow-write` | плюс изменения черновика версии: создание, тексты и настройки, загрузка APK и AAB, иконка и скриншоты, удаление черновика и скриншотов |
| destructive | `--allow-destructive` | плюс действия, которые доходят до пользователей или затрагивают деньги: отправка на модерацию, публикация, процент раскатки, архивирование, ответы на отзывы, возвраты, отмены и подтверждения покупок и подписок, выдача и отзыв доступов |

Отправка черновика на модерацию — уровень удаления: при автоматической публикации одобренная версия сразу уходит пользователям. Ответ на отзыв публичен, поэтому тоже требует `--allow-destructive`.

У каждого инструмента есть аннотации MCP: `readOnlyHint`, `destructiveHint`, `idempotentHint` (для изменяющих: `PUT` и `DELETE` идемпотентны, `POST` и `PATCH` — нет), `openWorldHint` и `title`.

Флаги командной строки важнее настроек профиля ([`serve`](cli.md#уровни-доступа-и-наборы)). Уровень доступа сервера не расширяет права ключа: RuStore всё равно проверяет методы API и приложения, отмеченные у ключа ([ключ RuStore API](cli.md#ключ-rustore-api)).

## Наборы инструментов

Набор — раздел справочника RuStore API. Без `--toolsets` и без настройки профиля включены `apps`, `releases` и `reviews`: этого хватает для выпуска версий и работы с отзывами. `--toolsets all` включает все наборы.

| Набор | Раздел справочника | Операций | По умолчанию |
| --- | --- | --- | --- |
| `apps` | Приложения: список приложений ключа, поиск приложения (`search_apps`) | 1 | да |
| `releases` | Версии и публикация: черновики, APK и AAB, статусы, модерация, публикация, раскатка, архив; сводка версий, загрузка сборки, отправка на модерацию и раскатка (`release_summary`, `upload_build`, `release_submit`, `release_rollout`) | 11 | да |
| `listing` | Иконка и скриншоты черновика; экспорт и применение текстов карточки, синхронизация скриншотов (`listing_export`, `listing_apply`, `sync_screenshots`) | 5 | |
| `reviews` | Отзывы, ответы разработчика, рейтинг, выгрузка отзывов в CSV; сводка и выгрузка отзывов (`reviews_summary`, `reviews_export`) | 8 | да |
| `purchases` | Платежи и покупки, возвраты; отчёт по платежам за период (`payments_report`) | 11 | |
| `subscriptions` | Подписки: данные, подтверждение, отмена | 8 | |
| `catalog` | Продуктовый каталог: продукты и подписки | 2 | |
| `access` | Доступы пользователей к приложению | 3 | |

В столбце «Операций» — инструменты операций API; [составные инструменты](#составные-инструменты) входят в свои наборы сверх этого числа.

Неизвестный набор — ошибка запуска со списком допустимых.

### Динамические наборы

Клиенты, которые не откладывают загрузку инструментов, кладут описания всех зарегистрированных инструментов в контекст модели сразу. С флагом `serve --dynamic-toolsets` (или `connect --dynamic-toolsets`, тогда настройка сохраняется в профиле) сервер при запуске регистрирует только:

- `api_search` и `api_request` — как обычно;
- [пользовательские инструменты](#пользовательские-инструменты) из `tools.toml` — их настроил пользователь, поэтому они регистрируются сразу и не входят ни в один набор;
- `list_toolsets` — наборы с разделом справочника, инструментами, доступными на текущем уровне, примерами имён, числом операций выше уровня доступа (`above_access_level`) и признаком `enabled`;
- `enable_toolset` — включить набор (аргумент `toolset`, можно несколько через запятую или `all`). Ответ перечисляет добавленные инструменты;
- `disable_toolset` — выключить набор, чтобы снова сократить список.

`--toolsets` (или наборы профиля) вместе с `--dynamic-toolsets` задают наборы, включённые при запуске; без них при запуске не включено ни одного набора. После `enable_toolset` и `disable_toolset` сервер отправляет клиенту `notifications/tools/list_changed` (в инициализации объявлена возможность `tools.listChanged`): в сессии с `initialize` — сразу после вызова, в протоколе MCP 2026-07-28 — по подписке `subscriptions/listen`. Клиент перечитывает `tools/list` и видит новые инструменты.

Уровень доступа действует как обычно: `enable_toolset` не регистрирует инструменты выше разрешённого уровня. Сами инструменты управления наборами — уровня чтения: они меняют только список инструментов сервера, а не данные RuStore, и к API не обращаются. Если клиент не перечитывает список инструментов, агент может вызвать ту же операцию через `api_request` (метод и путь подскажет `api_search`).

Динамические наборы работают только в stdio: HTTP-сервер ([HTTP-режим](http.md)) не хранит сессий, поэтому `--dynamic-toolsets` вместе с `--http` — ошибка запуска.

## Частые задачи

Для частых задач есть [составные инструменты](#составные-инструменты): они делают нужные запросы за один вызов и проверяют аргументы до отправки. Агенту достаточно попросить задачу словами, например «загрузи `app-release.aab` в черновик и отправь на модерацию с ручной публикацией»; ниже — какие инструменты он вызовет.

Инструменты текстов, скриншотов и платежей входят в наборы `listing` и `purchases`, которые по умолчанию выключены: включите их флагом `--toolsets` (например, `rustore-mcp connect claude-code --toolsets apps,releases,reviews,listing,purchases`) или работайте с [динамическими наборами](#динамические-наборы), тогда агент включит их сам.

### Загрузить сборку и отправить на модерацию

1. `release_summary` — что сейчас опубликовано, на модерации, в черновике и почему отклонена последняя версия (чтение).
2. `upload_build` с `aab` (или `apks`) и, при желании, `whatsNew` и `moderInfo` — загружает сборку в черновик: в существующий, а если черновика нет, создаёт новый. Возвращает `versionId` и состояние черновика. Пользователи ничего не видят (`--allow-write`).
3. `release_submit` с `dry_run: true` — проверяет, что у черновика есть сборка, и показывает план вызовов, ничего не меняя.
4. `release_submit` с `publishType` — отправка на модерацию (`--allow-destructive`). `INSTANTLY` (по умолчанию в RuStore) — версия уходит пользователям сразу после модерации, `MANUAL` — ждёт `release_rollout`, `DELAYED` — публикуется в `publishDateTime`. После отправки черновик менять нельзя.

Тексты черновика, кроме `whatsNew` и `moderInfo`, задаёт `listing_apply` или поле `draft_fields` у `upload_build`.

### Опубликовать и раскатить поэтапно

1. При отправке на модерацию задайте `publishType: "MANUAL"` и, если нужна поэтапная раскатка, `partialValue` (5, 10, 25, 50, 75 или 100 процентов).
2. `release_rollout` с `action: "status"` — статус одобренной версии, тип публикации, процент и следующий шаг (чтение, без изменений).
3. `release_rollout` с `action: "publish"` — ручная публикация версии в `READY_FOR_PUBLICATION`; с `partialValue` — сначала этой доле пользователей.
4. `release_rollout` с `action: "set_percent"` и большим `partialValue` — расширить раскатку; 100 — всем пользователям. Уменьшить процент RuStore не умеет, такой вызов отклоняется.

Шаги 3 и 4 доходят до пользователей сразу (`--allow-destructive`); у обоих есть `dry_run: true`.

### Ответить на отзывы

1. `reviews_summary` с `unanswered_only: true` (и, например, `max_rating: 3`, `days: 30`) — рейтинг, распределение по оценкам и по состоянию ответа и компактные записи отзывов с `commentId` (чтение).
2. `reply_to_review` с `commentId` и текстом в `body.message` (от 1 до 500 символов) — публичный ответ (`--allow-destructive`). Ответ сначала проходит модерацию RuStore: состояние покажет `get_review_answer_statuses` или следующий `reviews_summary`. Исправить ответ — `update_review_answer`, удалить — `delete_review_answer`.

Выгрузить отзывы в файл для анализа — `reviews_export` с `save_to` (CSV RuStore или JSON Lines).

### Экспортировать и изменить тексты карточки

1. `listing_export` с `dir` — пишет в каталог `listing.json` (тексты опубликованной версии или, с `draft: true`, черновика) и `images.json` (иконка и скриншоты с путями `sync_path`). Без `dir` возвращает то же в ответе (чтение).
2. Отредактируйте объект `listing` в `listing.json`.
3. `listing_apply` с тем же `dir` и `dry_run: true` — разница с черновиком по полям и проверка ограничений справочника; затем без `dry_run` — отправка изменённых полей в черновик (`--allow-write`). Черновик должен существовать: его создаёт `upload_build` или `create_draft_version`.

### Синхронизировать скриншоты

1. Разложите файлы по схеме `<каталог>/<устройство>/<ориентация>/<номер>.png`, например `screenshots/phone/portrait/0.png` (каталог `listing_export` подходит: пути подсказывает `sync_path` в `images.json`).
2. `sync_screenshots` с `dir` и `dry_run: true` — проверка файлов (формат, размер, стороны, ориентация) и план загрузок и удалений.
3. `sync_screenshots` без `dry_run` — загрузка в черновик (`--allow-write`). Лишние скриншоты черновика удаляются только с `delete_extra: true`; `skip_existing: true` не трогает занятые позиции.

### Отчёт по платежам

`payments_report` с `from` и `to` (период до 92 дней) и именем пакета или `appId` — число платежей, суммы подтверждённых и возвращённых по валютам, разбивка по статусам и продуктам (чтение). С `save_to` платежи дополнительно пишутся в новый CSV-файл. Проверить один платёж — `get_payment` с `invoiceId`.

### Операции напрямую

| Задача | Инструменты | Уровень |
| --- | --- | --- |
| Найти приложение, узнать `packageName` и `appId` | `search_apps` или `list_apps` | чтение |
| Посмотреть версии и их статусы | `list_versions` (`versionStatuses`, `filterTestingType: "ALL"` для альфа-версий), `get_version` | чтение |
| Выпустить версию по шагам | `create_draft_version` → `upload_apk` или `upload_aab` → `update_draft_version` → `submit_draft_for_moderation` → при ручной публикации `publish_version` | запись, затем удаление |
| Обновить иконку и отдельные скриншоты черновика | `upload_icon`, `list_screenshots`, `upload_screenshot_v2`, `delete_screenshot` | запись |
| Изменить тип и время публикации или процент раскатки | `update_publish_settings` | удаление |
| Перевести старую или отклонённую версию в архив (`ARCHIVED`) | `archive_version` | удаление |
| Прочитать отзывы и рейтинг | `list_reviews`, `get_app_rating`, `export_reviews_csv` (`save_to`) | чтение |
| Проверить платёж, покупку или подписку | `get_payment`, `list_payments_by_date`, `list_user_purchases`, `get_subscription_v5` | чтение |
| Вернуть платёж, отменить или подтвердить покупку или подписку | `refund_payment`, `cancel_purchase`, `confirm_purchase`, `cancel_subscription`, `acknowledge_subscription` | удаление |
| Проверить интеграцию платежей на тестовых покупках | инструменты `*_sandbox` | чтение, удаление |
| Выдать или отозвать доступ к приложению | `list_app_access`, `grant_app_access`, `revoke_app_access` | чтение, удаление |

У приложения может быть только один черновик: если `create_draft_version` вернул ошибку, найдите существующий черновик через `list_versions` с `versionStatuses: "DRAFT"` и продолжите его или удалите `delete_draft_version`. Причина отклонения версии — в поле `statusComment` ответа `get_version` (её показывает и `release_summary`).

Если нужной операции нет среди зарегистрированных, агент находит её через `api_search`: в ответе сказано, какой флаг или набор её включает, а вызвать её в пределах уровня доступа можно через `api_request`.

## Составные инструменты

Составной инструмент делает несколько запросов к RuStore API за один вызов и возвращает компактный результат. Он регистрируется по тем же правилам, что и инструменты операций: по уровню доступа и набору; `api_search` находит его наравне с операциями (`kind: "composite"`), а `list_toolsets` учитывает в своём наборе. Аргументы проверяются по схеме инструмента, результат проходит то же вырезание учётных данных, фильтр `jq` и лимит размера. Если имя пакета не передано, а в профиле один пакет по умолчанию (`connect --package`), берётся он. Как сочетать их в типичных задачах — в разделе [Частые задачи](#частые-задачи).

| Инструмент | Набор | Уровень | Что делает |
| --- | --- | --- | --- |
| `search_apps` | `apps` | чтение | Читает все страницы `list_apps` и ищет приложения по подстроке названия или имени пакета без учёта регистра (`query`), с фильтром по статусу (`status`) и пределом (`limit`, по умолчанию 50). Возвращает `packageName`, `appName`, `appId`, `appStatus`, `versionName`, `versionCode`, `appVerUpdatedAt`; точные совпадения и совпадения с начала — первыми. |
| `release_summary` | `releases` | чтение | Читает версии приложения (`list_versions`, до `scan` версий, по умолчанию 200) и группирует последние по состоянию: `active`, `partial` (с процентом `partialValue`), `ready_for_publication`, `in_moderation`, `draft`, `rejected` (с комментарием модерации `statusComment` из `get_version`). Старые версии только считаются в `status_counts`. `include_alpha: true` добавляет альфа-версии, `per_status` — сколько версий показать в группе (по умолчанию 3). |
| `upload_build` | `releases` | запись, локальные файлы | Загружает сборку в черновик версии: в черновик `versionId`, а без него — в существующий черновик приложения (новый создаётся, только если черновика нет; если `create_draft_version` вернул ошибку, берётся найденный после неё черновик). Сначала задаёт поля черновика (`whatsNew`, `moderInfo`, другие поля `update_draft_version` в `draft_fields`), затем загружает один AAB (`aab`) и APK (`apks`: путь или объект с `file`, `isMainApk`, `servicesType: HMS` для APK с Huawei Mobile Services; без AAB и явного `isMainApk` основным становится первый APK не для HMS). До запросов проверяет расширения `.aab` и `.apk`, размер до 5 ГБ, лимит один AAB и до 8 APK или до 10 APK, разрешённые каталоги. Возвращает `versionId`, `draft` (`created`, `reused`, `given`), загруженные файлы с найденными RuStore разрешениями и SDK и состояние черновика без ссылок на файлы. На модерацию не отправляет. В HTTP-режиме не регистрируется. |
| `release_submit` | `releases` | удаление | Отправляет черновик (`versionId` или черновик приложения) на модерацию (`submit_draft_for_moderation`, `priorityUpdate` от 0 до 5). Перед этим может задать публикацию через `update_draft_version`: `publishType` (`INSTANTLY` — выпуск пользователям сразу после модерации, по умолчанию в RuStore; `MANUAL` — ждать `release_rollout`; `DELAYED` с обязательным `publishDateTime`) и `partialValue` (5, 10, 25, 50, 75, 100; только при `INSTANTLY` и `MANUAL`). По умолчанию (`check_build: true`) проверяет через `get_version`, что версия — черновик со сборкой и не только с APK для HMS. `dry_run: true` читает состояние и возвращает план вызовов, ничего не меняя. В ответе — `after_moderation`: что произойдёт после модерации. |
| `release_rollout` | `releases` | удаление | Управляет публикацией версии в `PARTIAL_ACTIVE` или `READY_FOR_PUBLICATION` (`versionId`, без него — единственная такая версия): `action: status` — состояние и следующий шаг без изменений; `publish` — ручная публикация одобренной версии с типом `MANUAL` (`publish_version`), с `partialValue` — сначала процент через `update_publish_settings`; `set_percent` — новый процент раскатки (`update_publish_settings`). RuStore не умеет уменьшать процент, поэтому меньшее значение отклоняется, равное — ничего не меняет. `dry_run: true` возвращает план вызовов без изменений. |
| `reviews_summary` | `reviews` | чтение | Рейтинг приложения (`get_app_rating`) и последние отзывы со всех страниц `list_reviews` (новые первыми, до `scan` отзывов, по умолчанию 1000) с фильтрами: период (`from` и `to` в формате `ГГГГ-ММ-ДД` или последние `days` дней, по дате отзыва, UTC), оценки (`min_rating`, `max_rating`), `unanswered_only` (нет опубликованного ответа и ответа на модерации), подстрока текста без учёта регистра (`text`). Считает подошедшие отзывы по оценкам (`by_rating`) и по состоянию ответа (`by_answer_status`: `answered`, `answer_in_moderation`, `answer_rejected`, `unanswered` — по `get_review_answer_statuses`, `answer_statuses: false` отключает этот запрос) и возвращает до `limit` компактных записей (по умолчанию 20): `commentId` для ответа, оценка, дата, версия, текст (сокращается до `max_text_length`, по умолчанию 500), состояние и последний ответ разработчика. Имени автора и данных устройства в записях нет. |
| `reviews_export` | `reviews` | чтение, локальные файлы | Сохраняет все отзывы по тем же фильтрам в новый файл `save_to` (существующий не перезаписывается) и возвращает только путь и число записей. Если задан только период до 92 дней, а `format` — `auto` или `csv`, файл — CSV-выгрузка RuStore (`export_reviews_csv`, в ней есть имя автора). Иначе (фильтры оценок, ответа и текста, период длиннее или без периода, `format: jsonl`) — JSON Lines из `list_reviews`, по отзыву в строке: `commentId`, оценка, полный текст, даты, версия, `edited`, лайки, состояние и последний ответ разработчика; имя автора — только с `include_user_name: true`. В HTTP-режиме не регистрируется. |
| `payments_report` | `purchases` | чтение | Платежи приложения за период до 92 дней (`from`, `to` в формате `ГГГГ-ММ-ДД`): `list_payments_by_date` за каждый день, все страницы. Приложение — `appId` или имя пакета, по которому `appId` находится через `list_apps`. `statuses` ограничивает статусы счёта (по умолчанию все). Возвращает итоги: число платежей, суммы `CONFIRMED` и `REFUNDED` по валютам (`totals`), число и сумму по статусам (`by_status`) и по продуктам `order.itemCode` (`by_products`, до 50, больше платежей — выше). Суммы — в минимальных единицах валюты (копейки), из `order.amountCurrent`. С `save_to` платежи пишутся в новый CSV-файл (номер и даты счёта, статус, продукт, суммы, валюта, `purchaseId`, состояние выдачи; `appUserId` — только с `include_user_id: true`, данных карты нет). Отдельные платежи агенту не возвращаются. В HTTP-режиме `save_to` недоступен. |
| `listing_export` | `listing` | чтение, локальные файлы | Тексты карточки версии и сведения об изображениях. В RuStore тексты принадлежат версии: по умолчанию берётся самая новая опубликованная (`ACTIVE` или `PARTIAL_ACTIVE`), `draft: true` — черновик, `versionId` — любая версия. Поля: `appName`, `appType`, `categories`, `ageLegal`, `shortDescription`, `fullDescription`, `whatsNew`, тексты для ТВ, `developerContacts`, `faq`, `seoTagIds`, `privacyExplanation`, `inAppPurchaseTypes`, `video`, `backgroundVideo` — в виде, который принимает `update_draft_version`. Без `dir` возвращает всё в ответе, с `dir` пишет в каталог `listing.json` (поля в объекте `listing`) и `images.json` (иконка, скриншоты с типом, ориентацией, номером и `sync_path` — путём, по которому файл ждёт `sync_screenshots`). Каталог может быть новым (родитель должен существовать) или существующим без этих файлов; существующие файлы не перезаписываются. Картинки не скачиваются: ссылки `fileUrl` и `iconUrl` ведут в хранилище RuStore, а сервер обращается только к RuStore API. В HTTP-режиме не регистрируется. |
| `listing_apply` | `listing` | запись, локальные файлы | Применяет тексты к черновику: из `listing.json` в каталоге `dir` (формат `listing_export`) или из аргумента `listing`. Сравнивает каждое поле с черновиком (`get_version`) и отправляет `update_draft_version` только с изменёнными; `dry_run: true` возвращает разницу по полям (длинные тексты — построчно) и ничего не меняет, `fields` ограничивает набор полей. До запросов проверяет ограничения справочника: `appName` до 50 символов, `shortDescription` до 80, `fullDescription` до 4000, `whatsNew` до 5000, `moderInfo` до 180, не больше 2 категорий, 10 вопросов `faq`, 5 `seoTagIds` и т. д. Поля без значения или `null` не меняются. Нужен существующий черновик: без `versionId` берётся черновик приложения, если его нет — сначала `create_draft_version`. В HTTP-режиме не регистрируется. |
| `sync_screenshots` | `listing` | запись, локальные файлы | Синхронизирует скриншоты черновика с локальным каталогом `dir`: `<устройство>/<ориентация>/<номер>.png` (или `.jpg`, `.jpeg`), устройство — `phone`, `tablet`, `tv` (`SCREENSHOT`, `TABLET_SCREENSHOT`, `TV_SCREENSHOT`), ориентация — `portrait` или `landscape`, номер — позиция RuStore от 0 до 9, например `phone/portrait/0.png`; `portrait/0.png` в корне — сокращение для телефона; у каталога `listing_export` берётся подкаталог `screenshots/`. Синхронизируются только типы устройств, для которых есть каталог. До запросов проверяет файлы: PNG или JPEG по содержимому и расширению, до 5 МБ, стороны от 320 до 3840 пикселей, ориентация каталога, одна ориентация на тип устройства; соотношение сторон не 16:9 или 9:16 — предупреждение. RuStore не отдаёт хеш и размер загруженных скриншотов, поэтому изменённый файл не отличить: по умолчанию каждый локальный файл загружается заново (`upload_screenshot_v2` заменяет скриншот на этой позиции), `skip_existing: true` пропускает занятые позиции. Скриншоты черновика без локального файла и скриншоты другой ориентации удаляются только с `delete_extra: true` (другая ориентация — до загрузок). `dry_run: true` возвращает план. В HTTP-режиме не регистрируется. |

## Аргументы и ответы

- Параметры пути и строки запроса — аргументы с именами из API (`packageName`, `versionId`, `appId`, `page`, `size`); массив в строке запроса передаётся повторением ключа. JSON-тело запроса — аргумент `body`, файл для загрузки — путь в аргументе `file`. Неизвестные аргументы и пропущенные обязательные — ошибка до отправки запроса.
- Методы приложений, версий, изображений, отзывов и доступов принимают имя пакета (`packageName`), методы платежей, покупок, отмены подписок и каталога — числовой идентификатор приложения (`appId` из `list_apps`).
- RuStore возвращает ответы в конверте `{"code", "message", "body", "timestamp"}`. Инструмент возвращает `body` (или весь конверт, если `body` пустой); `code`, отличный от `OK`, — ошибка с сообщением RuStore даже при HTTP 200.
- Ошибки RuStore (`4xx`, `5xx`) возвращаются агенту как ошибка инструмента (`isError: true`) с кодом и сообщением; сервер продолжает работать.
- Значения, похожие на учётные данные, заменяются на `[redacted]` во всех ответах, в том числе в ошибках; к результату добавляется пометка, что и сколько скрыто. Подробности — в разделе [Учётные данные в ответах](security.md#учётные-данные-в-ответах).
- Описание каждого инструмента операции заканчивается ссылкой на страницу справочника.

## api_search и api_request

Два инструмента регистрируются всегда, независимо от `--toolsets` и `--dynamic-toolsets`:

- `api_search` ищет по всем операциям спецификации, в том числе выключенным: по имени инструмента, `operationId`, описанию, пути и разделу справочника. Запрос можно писать по-английски и по-русски: русские слова сравниваются по основе и переводятся в имена из API («черновик» находит `create_draft_version` и `submit_draft_for_moderation`, «отзыв» — операции `comment` и `review`, «скриншот», «платёж», «подписка», «доступ» — операции своих разделов). В каждом результате — имя инструмента, метод, путь, уровень доступа, набор, обязательные параметры, ссылка на справочник, зарегистрирован ли инструмент и, если нет, каким флагом его включить (`--allow-write`, `--allow-destructive`, `--toolsets <набор>`). Аргумент `tool_name` возвращает полную схему аргументов одной операции; `toolset` ограничивает поиск набором; `limit` — число результатов (по умолчанию 20, не больше 100). В API инструмент не обращается и всегда только читает. С `--dynamic-toolsets` для операции из выключенного набора он подсказывает вызов `enable_toolset`.
- `api_request` отправляет запрос к любому пути RuStore API: `method`, `path` (начинается с `/public/`, например `/public/v1/application/com.example.app/version`), `query` (объект; массив передаётся повторением ключа), `body` (JSON), `jq` ([фильтр ответа](#фильтр-ответа-jq)) и `save_to` для скачивания файлов. Заголовки задать нельзя: `Public-Token` добавляет сервер. Полные URL, `?`, `#`, `..` и путь получения токена `/public/auth/` отклоняются.

Уровень доступа `api_request` определяется по спецификации: запрос сопоставляется с шаблонами путей операций (литеральные сегменты без учёта регистра и после percent-раскодирования), и действует уровень совпавшей операции — при нескольких совпадениях максимальный. Поэтому `POST …/version/{versionId}/commit` (отправка на модерацию) требует `--allow-destructive`, хотя это `POST`. Путь, которого нет в спецификации, оценивается по методу: `GET` — чтение, `DELETE` — удаление, остальные — запись. Запрос выше уровня сервера не отправляется: агент получает ошибку с флагом, который нужен.

Аннотации `api_request` соответствуют уровню сервера: `readOnlyHint` в режиме чтения, `destructiveHint` с `--allow-destructive`. `save_to` принимается только для операций, которые возвращают файл (выгрузка отзывов в CSV): JSON-ответ в файл не сохраняется, он возвращается в результате с теми же заменами учётных данных.

## Постраничная выдача

В RuStore API два вида постраничной выдачи:

- **Номер страницы.** Версии, отзывы, ответы на отзывы и скриншоты принимают `page` (с нуля) и `size`, платежи по дате — `pageNumber` и `pageSize`. Если в ответе есть массив `content` и итоги выдачи, ответ оборачивается: `{"result": <ответ>, "pagination": {"page", "page_size", "total_pages", "total_elements", "next_page", "pass_as"}}`. Следующая страница — тот же вызов с `next_page` в аргументе из `pass_as`; на последней странице `next_page` нет.
- **Токен продолжения.** Список приложений и продуктовый каталог возвращают `continuationToken`, доступы — `pageToken`, покупки пользователя принимают `continuation`. Токен передаётся в следующем вызове в аргументе с тем же именем, пока он есть в ответе. Для `list_apps` нужны ещё `pagination: true` и `pageSize`.

Ответ больше `--max-response-bytes` (256 КиБ по умолчанию) не обрезается, а возвращается ошибкой с подсказкой сузить запрос: уменьшите `size` или `pageSize`, отфильтруйте по статусу или дате или оставьте нужное [фильтром `jq`](#фильтр-ответа-jq).

## Фильтр ответа jq

Ответы RuStore бывают большими: версия с описаниями и списком файлов или страница отзывов быстро занимают контекст агента. Инструменты операций, `api_request` и [пользовательские инструменты](#пользовательские-инструменты) принимают необязательный аргумент `jq` — фильтр на языке [jq](https://jqlang.org/manual/) (диалект [jaq](https://github.com/01mf02/jaq)), который применяется к JSON-ответу до возврата агенту:

```json
{
  "packageName": "com.example.app",
  "jq": "[.content[] | {versionId, versionName, versionStatus}]"
}
```

- **Порядок обработки:** замена учётных данных на `[redacted]` → фильтр → лимит размера. Фильтр получает уже очищенный ответ, поэтому никакой фильтр (например, `.. | strings`) не раскрывает скрытые значения. Лимит `--max-response-bytes` применяется к результату фильтра; исходный ответ для фильтра читается до 16 МиБ. Результат больше лимита — ошибка с пометкой, что сам запрос выполнен.
- **Постраничная выдача.** Если ответ обёрнут в `{"result": …, "pagination": …}`, фильтр применяется к телу ответа RuStore, а `pagination` остаётся рядом: `{"result": <результат фильтра>, "pagination": {…}}`.
- **Результат:** ровно один результат фильтра возвращается как есть; несколько — JSON-массивом (`.content[] | .versionId` → `[1, 2]`); ни одного — `[]`.
- **Ошибки.** Синтаксис и имена функций проверяются до запроса к API: неверный фильтр — ошибка `isError: true`, а запрос не отправляется. Если фильтр упал при выполнении, ошибка сообщает, что сам запрос к API выполнен: запрос, изменяющий данные, повторять не нужно.
- **Ответ не в JSON** (текст, пустое тело) возвращается без фильтра, с пояснением. У инструментов, которые сохраняют файл (`save_to`), аргумента `jq` нет; `api_request` с `jq` и `save_to` одновременно — ошибка.
- **Ограничения фильтра.** Длина — до 4096 байт. Недоступны окружение процесса (`env`, `$ENV`), входные потоки (`input`, `inputs`) и модули (`import`, `include`); `debug` и `stderr` ничего не выводят, `halt` — ошибка. Фильтр выполняется в отдельном процессе с пустым окружением и прерывается через 10 секунд: зацикленный или бесконечно рекурсивный фильтр возвращает ошибку и не влияет на сервер.

## Пользовательские инструменты

Частые запросы можно оформить именованными инструментами, чтобы агент не собирал их каждый раз заново: например, «черновики моего приложения». Пользовательский инструмент вызывает одну операцию RuStore API с фиксированными аргументами и необязательным фильтром `jq`. Инструменты описываются в TOML:

- `tools.toml` в каталоге конфигурации рядом с `profiles.toml` (`~/.config/rustore-mcp/tools.toml`; каталог можно переопределить переменной `RUSTORE_MCP_CONFIG_DIR`, на Linux учитывается `XDG_CONFIG_HOME`, в Windows — `%APPDATA%`) — читается при каждом запуске `serve`, если файл есть;
- другие файлы — только явно, флагом `serve --tools-file <путь>` (можно повторять). Файл из репозитория проекта — недоверенный ввод, поэтому клонирование репозитория само по себе инструментов не добавляет.

В [HTTP-режиме](http.md) читаются только файлы из `--tools-file` — на машине сервера при запуске. Инструменты над операциями с локальными файлами там не регистрируются.

```toml
[[tools]]
name = "my_app_drafts"
description = "Draft versions of the main app: id, name and status only"
operation = "list_versions"
jq = "[.content[] | {versionId, versionName, versionStatus}]"

[tools.args]
packageName = "com.example.app"
versionStatuses = "DRAFT"

[[tools]]
name = "my_app_rating"
description = "Rating of the main app"
operation = "get_app_rating"
args = { packageName = "com.example.app" }
```

| Поле | Назначение |
| --- | --- |
| `name` | Имя инструмента: строчные латинские буквы, цифры и `_`, начинается с буквы, до 64 символов. |
| `description` | Описание для агента (обязательно). Сервер дополняет его операцией, фиксированными аргументами и ссылкой на справочник. |
| `operation` | Имя инструмента операции API (`list_versions`, `get_version`, `list_reviews`; найти — `api_search`). |
| `args` | Фиксированные аргументы операции (TOML-таблица): параметры пути и запроса с именами из API и `body` целиком. Значения проверяются по схеме операции. |
| `jq` | [Фильтр ответа](#фильтр-ответа-jq), который применяется всегда. |

Фиксированные аргументы убираются из схемы инструмента: агент передаёт только остальные аргументы операции, а попытка передать фиксированный — ошибка. Нельзя фиксировать `save_to` и файловые аргументы (пути проверяются при каждом вызове), а также `null`. Кроме аргументов операции, пользовательский инструмент принимает `jq`: фильтр из вызова применяется после фильтра из файла.

Уровень доступа и аннотации инструмента — как у его операции; инструменты выше уровня сервера не регистрируются, а вызов такого инструмента объясняет, какой флаг нужен. Наборы инструментов (`--toolsets`) пользовательские инструменты не ограничивают; с `--dynamic-toolsets` они регистрируются сразу при запуске, без `enable_toolset`.

Ошибки в файле останавливают запуск сервера с понятным сообщением (файл и инструмент): неверный TOML, неизвестные поля, неизвестная операция или аргумент, неверный фильтр. Имя, совпадающее со встроенным инструментом (с любой операцией API, составным инструментом, `api_request`, `api_search`, `list_toolsets`, `enable_toolset`, `disable_toolset`) или с другим пользовательским инструментом, — тоже ошибка запуска, а не тихий пропуск. Проверить файлы заранее можно командой [`rustore-mcp tools check`](cli.md#tools).

## Локальные файлы

Инструменты загрузки (`upload_apk`, `upload_aab`, `upload_icon`, `upload_screenshot`, `upload_screenshot_v2`) принимают в аргументе `file` путь к файлу, а инструменты, которые возвращают файл (`export_reviews_csv`, `api_request` для таких операций), сохраняют его по пути из `save_to`. Пути должны быть внутри разрешённых каталогов: рабочего каталога сервера, системного временного каталога и каталогов из `--allow-path` ([подробнее](security.md#локальные-файлы)). Составные инструменты работают с файлами так же: `upload_build` загружает сборки из `aab` и `apks`, `reviews_export` и `payments_report` пишут новый файл `save_to`, `listing_export`, `listing_apply` и `sync_screenshots` пишут и читают каталог `dir`. Существующие файлы не перезаписываются. В [HTTP-режиме](http.md#как-это-устроено) инструменты с локальными файлами не регистрируются, а `save_to` у `payments_report` недоступен.

## Инструкции сервера

При подключении сервер передаёт агенту инструкции: уровень доступа и включённые наборы, имена пакетов по умолчанию из профиля, как устроен выпуск версии (черновик, сборка, модерация, публикация, один черновик на приложение, статусы) и составные инструменты для него (`upload_build` → `release_submit` → `release_rollout`), чем отличаются инструменты песочницы, как найти выключенную операцию, как включать наборы (с `--dynamic-toolsets`), какие есть пользовательские инструменты, как работать с постраничной выдачей, большими ответами и фильтром `jq`, какие каталоги разрешены для файлов, что ключ и токен никогда не передаются в аргументах и не запрашиваются в чате и что делать при `401` и `403`. Отдельно сказано не переносить персональные данные из ответов в логи, коммиты и код без просьбы пользователя.
